# H8 — Retry non destructif et garde-fous

## 1. Problem

Quand une erreur transitoire survient après le premier chunk, le retry de session relance tout le stream
depuis zéro : le texte déjà streamé est jeté et re-facturé, et aucun timeout d'inactivité ne borne par
défaut un stream qui cale.

## 3. Mechanism

1. `processor.process` entre dans le `Effect.gen` qui ouvre le stream (`processor.ts:970-987`).
2. Le drain (`:978-982`) laisse `handleEvent` écrire du texte (`ctx.currentText`) au fil des chunks.
3. Une erreur transitoire (5xx/429, classification `retry.ts:75-129`) remonte ; `Effect.retry(SessionRetry.policy({…}))`
   (`:1001`) décide de retenter.
4. La reprise ré-exécute **tout** le `Effect.gen` : `ctx.currentText = undefined` (`:972`) puis
   `llm.stream(streamInput)` (`:976`) — un `streamText` neuf, le préfixe complet re-envoyé.
5. Le texte déjà reçu au point 2 est perdu côté assistant et re-facturé côté provider.
6. En absence de `streamTimeoutMs`, un stream qui reçoit un premier chunk puis cale n'a **aucune** borne :
   `baseStream` est retourné tel quel (`llm.ts:524-525`), le drain attend indéfiniment.

## 4. Proposal

Trois correctifs alignés :

- **Retry non destructif** : ne retenter le stream que tant qu'**aucun** contenu n'a été streamé pour ce
  step ; si du texte a déjà été produit, halter (surface d'erreur) au lieu de repartir de zéro — le travail
  déjà payé n'est ni jeté ni re-facturé.
- **Timeout d'inactivité par défaut** : activer `streamTimeoutMs` avec une valeur par défaut bornée,
  débrayable, plutôt que `undefined`.
- **Alignement des couches** : plafonner la composition (`executor MAX_RETRIES` × politique de session)
  pour que le nombre total de tentatives soit borné.

Fichiers modifiés : `packages/opencode/src/session/processor.ts` (garde de retry),
`packages/opencode/src/session/llm.ts` (défaut de timeout), `packages/opencode/src/effect/runtime-flags.ts`
(défaut), `packages/llm/src/route/executor.ts` (plafond aligné).

Code cible (≤ 15 lignes) :

```ts
// session/processor.ts — retry seulement si rien n'a encore été streamé
Effect.retry({
  while: () => ctx.currentText === undefined || ctx.currentText === "",
  schedule: SessionRetry.policy({ ... }),
}),

// session/llm.ts — borne d'inactivité par défaut
const streamTimeoutMs = flags.streamTimeoutMs ?? 120_000 // 120 s, débrayable
```

Reste **volontairement** inchangé :

- le délai/backoff (`retry.ts:42-73`) : la correction porte sur *ce qu'on retente*, pas sur *combien de
  temps on attend* ;
- la classification des erreurs retryables (`retry.ts:75-159`) : inchangée ;
- l'exemption des tours qui attendent l'utilisateur (`llm.ts:514-522`) : le timeout par défaut doit rester
  au-dessus du temps de réponse humaine typique, ou rester désactivable (point à trancher, §10).

## 5. Alternatives considered

1. **Supprimer le retry de session.** Écartée : perd la résilience aux erreurs transitoires (5xx/429) que
   le harnais exploite déjà (`retry.ts:80-82`).
2. **Augmenter le nombre de tentatives** pour « passer » l'erreur. Écartée : aggrave la re-facturation
   (chaque tentative repart de zéro) ; contraire à l'objectif.
3. **N'ajouter que le timeout, laisser le retry destructif.** Écartée : traite le blocage mais pas la
   double facturation, qui est le critère principal du BACKLOG.
4. **Conserver le texte déjà streamé comme préfixe assistant et demander une continuation au provider.**
   Écartée ici : suppose que le provider sache reprendre un stream ; non garanti par le protocole
   openai-compatible, donc hors périmètre de ce correctif (voir §10).

## 6. Risks

- **Régression tests existants** (fichiers réels) :
  `packages/opencode/test/session/retry.test.ts` (cœur de la politique),
  `packages/opencode/test/session/processor-effect.test.ts`,
  `packages/opencode/test/session/llm.test.ts`,
  `packages/opencode/test/session/llm-native.test.ts`,
  `packages/opencode/src/session/prompt-budget.test.ts` (le budget contextuel dépend du nombre de tentatives),
  `packages/opencode/src/session/step-limit.test.ts`.
- **Coût tokens** : le correctif **réduit** les tokens facturés (suppression de la re-facturation) ; aucun
  coût ajouté en tokens.
- **Latence** : le timeout par défaut ajoute une borne ; il ne s'ajoute pas au chemin nominal (il ne se
  déclenche que sur inactivité). Risque : un tour légitime lent (outil long silencieux) pourrait être coupé
  trop tôt si le défaut est bas ⇒ la valeur par défaut doit rester au-dessus du temps de réponse humaine
  typique, ou rester désactivable.
- **Sécurité** : aucune. La garde de retry ne touche pas aux permissions ; le timeout est un garde-fou,
  pas un contournement.

## 7. Acceptance (critère monotone)

Critères **absolus** (jamais un ratio dont le dénominateur serait une grandeur que le patch fait baisser) :

1. **Non re-facturation** — sur une erreur transitoire injectée **après le premier chunk**, le total de
   tokens facturés du tour ne dépasse pas celui d'un stream unique réussi :
   `billed_tokens_after_error <= billed_tokens_reference` (absolu). Grandeur mesurée : `usage`/`cost`
   accumulés (`processor.ts:729-730`).
2. **Interruption d'un stream qui cale** — un stream qui n'émet plus est interrompu par le timeout : temps
   mural ≤ (timeout configuré + marge), au lieu de pendre. Grandeur mesurée : latence murale absolue (ms)
   et fin de stream observée (`StreamTimeoutError`, `llm.ts:41`).
3. **Résilience préservée** — une erreur **avant tout chunk** reste retentée et réussit (le comportement
   actuel n'est pas perdu).

Commande de mesure : `cd packages/opencode && bun test --timeout 30000 ./test/session/retry-non-destructive.test.ts`.
Valeurs attendues : `billed_tokens_after_error <= reference`, `wall_ms <= timeout + margin`,
`retry_before_first_chunk_succeeds === true`. Comparaison à `../BASELINE.md`.

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/retry-non-destructive.test.ts`.

Commande : `bun test --timeout 30000 ./test/session/retry-non-destructive.test.ts`.

Cas, avec critère observable :

1. **Erreur après premier chunk** — provider scripté qui émet un chunk puis une erreur 5xx : succès = le
   stream est halté, le texte déjà reçu (`ctx.currentText`) est conservé (pas de remise à zéro), total
   facturé == un seul stream.
2. **Test par mutation (garde de retry)** — neutraliser la garde `ctx.currentText === undefined` doit
   **reproduire** la double facturation (le test 1 échoue) ⇒ prouve que la garde marche, pas seulement
   qu'elle est présente.
3. **Erreur avant premier chunk** — provider qui échoue avant tout chunk : succès = retry, puis succès du
   stream, total de tentatives borné.
4. **Stream qui cale** — provider qui émet un chunk puis n'émet plus : succès = fin de stream par
   `StreamTimeoutError` dans `timeout + marge`, session non bloquée.

Régression : relancer `test/session/retry.test.ts`, `test/session/processor-effect.test.ts`,
`test/session/llm.test.ts`.

## 9. Effort

`M` — la garde de retry touche le cœur du cycle de vie du stream (`processor.process`), et l'alignement
des deux couches de retry exige de raisonner sur leur composition.

## 10. Verdict self-assessment

`NEEDS_REVIEW` — question à trancher par le validateur : **que signifie « non destructif » au niveau du
protocole ?** La fiche choisit (i) *ne pas retenter du tout* dès qu'un contenu a été streamé, ce qui
garantit l'absence de re-facturation mais renonce à la reprise sur erreur transitoire tardive.
L'alternative (ii) — conserver le préfixe déjà streamé et demander une continuation — supposerait que le
provider openai-compatible sache reprendre un stream, ce que la fiche n'a pas pu prouver
(`INFERE:` non vérifié). Le choix (i)/(ii) change le comportement observable en cas d'erreur tardive et
doit être tranché avant merge.
