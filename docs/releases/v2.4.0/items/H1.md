# H1 — Un seul appel provider par round d'outils

## 1. Problem

Dans un même tour d'agent, chaque round d'outil rouvre une requête provider complète et distincte :
un tour à 5 rounds d'outils paie 5 appels provider, donc 5 ré-assemblages de prompt, 5 injections de
contexte volatil et 5 cycles de vie de stream, là où le SDK sait enchaîner ces rounds dans un seul appel.

## 2. Evidence

**Le SDK `ai` est appelé sans borne de steps.** `packages/opencode/src/session/llm.ts:367` ouvre le bloc
`streamText({…})`, qui court jusqu'à `:437`, et n'y passe ni `stopWhen` ni `maxSteps` — `llm.ts:400-407` :

```
        activeTools: Object.keys(prepared.tools).filter((x) => x !== "invalid"),
        tools: prepared.tools,
        toolChoice: input.toolChoice,
        maxOutputTokens: prepared.params.maxOutputTokens,
        abortSignal: input.abort,
        headers: prepared.headers,
        maxRetries: input.retries ?? 0,
        messages: prepared.messages,
```

**Le défaut de `stopWhen` du SDK est un step unique** —
`node_modules/.bun/ai@6.0.168+3c5d820c62823f0b/node_modules/ai/dist/index.js:4122` :

```
  stopWhen = stepCountIs(1),
```

(même défaut pour la variante `streamText` en `index.js:6459` : `stopWhen = stepCountIs(1),`.)

**Les outils portent déjà un `execute`.** `LLMRequestPrep.prepare` construit `prepared.tools`
(`llm.ts:167`) et le code de repli y lit `t.execute` — `llm.ts:216-221` :

```
          const t = prepared.tools[toolName]
          if (!t || !t.execute) {
            ...
            const result = await t.execute!(JSON.parse(argsJson), {
              toolCallId: _requestID,
```

⇒ une boucle SDK multi-step peut exécuter les outils sans pont supplémentaire.

**Le tour est une boucle externe qui rappelle le provider à chaque itération.** `prompt.ts:1758`
(`while (true) {`), `:1933` (`step++`), `:2559` :

```

```

Chaque itération assemble `system`/`messages`/`volatile` puis appelle `handle.process`, qui ouvre un
nouveau stream — `packages/opencode/src/session/processor.ts:976-982` :

```
            const stream = llm.stream(streamInput)

            yield* stream.pipe(
              Stream.tap((event) => handleEvent(event)),
              Stream.takeUntil(() => ctx.needsCompaction),
              Stream.runDrain,
            )
```

**La surface d'événements est déjà indexée par step.** Le mapping SDK → `LLMEvent` gère
`start-step`/`finish-step` avec un index croissant — `packages/opencode/src/session/llm/ai-sdk.ts:74-80` :

```
    case "start-step":
      return Effect.succeed([LLMEvent.stepStart({ index: state.step })])
    case "finish-step":
      ...
        LLMEvent.stepFinish({
          index: state.step++,
```

Le processeur consomme ces événements comme `step-start`/`step-finish` et y accumule usage/cost —
`processor.ts:679`, `:706`, `:729-730` :

```
            ctx.assistantMessage.finish = value.reason
            ctx.assistantMessage.cost += usage.cost
            ctx.assistantMessage.tokens = usage.tokens
```

**BASELINE (reprise, non re-mesurée)** : `docs/releases/v2.4.0/BASELINE.md:60` — « appels provider par
round d'outils : par construction (`stopWhen = stepCountIs(1)`), 1 par round (cible H1 : 1 pour N rounds) ».

## 3. Mechanism

Chemin de bout en bout qui produit le coût :

1. `prompt.ts` entre dans `while (true)` (`:1758`) ; à l'itération `step`, il assemble `system`,
   `modelMsgs` et `volatile` (`:2552-2553`).
2. Il appelle `handle.process({…})` (`:2559`) avec les messages du tour.
3. `processor.process` (`processor.ts:963`) réinitialise le texte courant (`:972`, `ctx.currentText = undefined`)
   puis ouvre `llm.stream(streamInput)` (`:976`) et draine le stream (`:978-982`).
4. `llm.stream` → `run` → `streamText({…})` (`llm.ts:367`) : comme `stopWhen` n'est pas passé, le SDK
   applique `stepCountIs(1)` (`index.js:4122`) et n'exécute **qu'un** step.
5. Le step émet un `tool-call` ; `handleEvent` dispatche l'outil (`processor.ts:679`/`:706` encadrent
   start/finish), puis le stream se termine avec `finish="tool-calls"`.
6. `prompt.ts` ne sort pas : `handle.message.finish` reste `tool-calls`, la boucle repart à l'étape 1
   pour le round suivant (`:2592`, `:2655`). **Chaque round repasse donc par 2-4** : un `streamText`
   neuf, un prompt entier re-assemblé, un nouveau cycle de vie de stream.

Le correctif du §4 supprime l'étape 6 : c'est le SDK qui enchaîne les rounds à l'intérieur d'un même
`streamText`, et `prompt.ts` n'itère qu'une fois par tour.

## 4. Proposal

**Activer la continuation multi-step native, bornée et configurable.**

Fichiers modifiés :

- `packages/opencode/src/session/llm.ts` — passer `stopWhen: stepCountIs(n)` à `streamText`, `n` plafonné
  et issu de la config (`experimental.max_provider_steps`, défaut borné).
- `packages/opencode/src/session/prompt.ts` — quand un tour a chaîné `k` steps internes, décrémenter le
  budget de steps du tour (`agent.steps`, `prompt.ts:2083`) de `k-1` au lieu de laisser `step++` (`:1933`)
  compter une seule itération pour plusieurs rounds ; `reachedStepLimit`/`isLastStep` (`:320-321`, `:2084`)
  restent l'autorité du budget.

Code cible (≤ 15 lignes) :

```ts
// session/llm.ts — dans streamText({…}), après `messages: prepared.messages,`
        stopWhen: stepCountIs(Math.max(1, input.maxSteps ?? 8)),

// session/prompt.ts — après `handle.process`
        const internalSteps = handle.message.steps ?? 1 // nb de steps SDK du tour
        step += internalSteps - 1                        // rounds internes ≠ itérations
```

Reste **volontairement** inchangé, avec la raison :

- la surface `start-step`/`finish-step` → `step-start`/`step-finish` (`ai-sdk.ts:74-80`,
  `processor.ts:679`/`:706`) : elle est déjà indexée par step, donc N steps produisent N paires
  d'événements comme aujourd'hui — aucun consommateur ne voit de différence de forme ;
- l'accumulation usage/coût par step (`processor.ts:729-730`) : elle reste par step, donc le total
  facturé est identique et correct ;
- `turn_plan`, `continuation`, `stall-watch` : ils sont **par tour**, pas par round (voir §4.1).

### 4.1 Preuve mécanisme par mécanisme (exigence BACKLOG)

- **`turn_plan`** — piloté dans la boucle externe de `prompt.ts`, une fois par tour : `TurnPlan.enabled`/
  `TurnPlan.instruction` (`turn-plan.ts:200`, `:210`), appelés à `prompt.ts:1851-1872`. Il ne s'exécute
  **pas** dans `processor.process` ; réduire le nombre d'itérations à **une par tour** le laisse s'exécuter
  exactement comme aujourd'hui (une fois).
- **`continuation`** — `decideRunDecision` (`continuation.ts:61`) est appelé à `prompt.ts:1908-1916`
  (`AUTO_CONTINUE_LIMIT`, `continuation.ts:5`) sur le résultat de tour ; il ne dépend pas du nombre de
  rounds. Le journal `auto-continue` (`prompt.ts:1916`) reste émis au même endroit.
- **`stall-watch`** — `StallWatch.arm` (`stall-watch.ts:20`) est armé à `prompt.ts:1768` et relâché par
  `reachedProvider` (`:2558`), **avant** `handle.process`. Il borne la phase pré-provider d'un tour ; il
  reste armé une fois par tour.
- **compaction** — `ctx.needsCompaction` est posé dans `handleEvent` et
  `Stream.takeUntil(() => ctx.needsCompaction)` (`processor.ts:980`) arrête le drain au bon moment, y
  compris en multi-step ; `prompt.ts:2605` traite `result === "compact"`.

## 5. Alternatives considered

1. **Ne rien changer et se contenter de H2/H3 (cache explicite + préfixe stable).** Écartée : H2/H3
   réduisent le coût *par* appel mais ne suppriment pas les appels redondants ; le gain de H1 est
   multiplicatif avec eux, pas concurrent.
2. **Déplacer la boucle multi-step dans `prompt.ts` (enchaîner les rounds sans repasser par `streamText`).**
   Écartée : `streamText` est l'unique frontière SDK ; réimplémenter l'enchaînement hors SDK revient à
   refaire le travail du SDK et casse la surface d'événements (`ai-sdk.ts:74-80`).
3. **Passer `maxSteps` (API dépréciée) au lieu de `stopWhen`.** Écartée : le SDK 6.x expose `stopWhen` ;
   `maxSteps` n'est conservé que pour compatibilité.

## 6. Risks

- **Régression tests existants** (fichiers réels) :
  `packages/opencode/test/session/llm.test.ts`,
  `packages/opencode/test/session/llm-native.test.ts`,
  `packages/opencode/test/session/llm-native-recorded.test.ts`,
  `packages/opencode/test/session/processor-effect.test.ts`,
  `packages/opencode/test/session/prompt.test.ts`,
  `packages/opencode/test/session/context-rollout.test.ts`,
  `packages/opencode/src/session/prompt-budget.test.ts` (le nombre d'injections par tour change de cadence),
  `packages/opencode/src/session/step-limit.test.ts` (le budget de steps est re-calculé),
  `packages/opencode/src/session/turn-plan.test.ts`, `packages/opencode/src/session/continuation.test.ts`.
- **Budget de steps** : si `step += internalSteps - 1` est mal fait, `agent.steps` (`prompt.ts:2083`) peut
  être dépassé (tour trop long) ou tronqué (tour coupé trop tôt). C'est le risque fonctionnel principal ;
  traité par le test du §8 et `step-limit.test.ts`.
- **Coût tokens / latence** : le SDK émet **une requête HTTP par step interne** — le correctif ne change
  pas le nombre de *complétions* ; il supprime par round la ré-assemblage de prompt et le cycle de stream
  côté opencode. Gain attendu : `(N-1) ×` (injection volatile + framing de stream) par tour, à mesurer ;
  pas un gain sur les tokens de complétion. Le préfixe stable d'un tour enchaîné peut en revanche
  améliorer `cache_read` (sujet H2/H3).
- **Sécurité** : le multi-step exécute plus d'appels d'outils dans un seul `streamText` ; les gates de
  permission (`ask`) et le garde `doom_loop` (`processor.ts:563`) restent dans `handleEvent` et
  s'appliquent par tool-call, indépendamment du nombre de steps ⇒ pas de contournement, à condition de ne
  pas déplacer l'exécution d'outil hors du processeur.

## 7. Acceptance (critère monotone)

Critères **absolus** (aucun ratio dont le dénominateur serait une grandeur que le patch fait baisser) :

1. **Appels provider orchestrés** — sur un scénario à 5 rounds d'outils, le nombre d'invocations de
   `streamText` (une par `handle.process` aujourd'hui) passe de **5** à **≤ 2** (cible `../BASELINE.md:60` :
   « 1 pour N rounds »). Grandeur mesurée : compteur d'invocations provider par scénario.
2. **Tokens facturés** — le total de tokens facturés du scénario ne doit **pas augmenter** et vise `<` la
   valeur de référence.
3. **`cache_read`** — le total `cache_read` du scénario ne doit **pas diminuer** (`session.ts:426`,
   `read: cacheReadInputTokens` ; agrégé `session.sql.ts:48`, `tokens_cache_read`).
4. **Non-régression des mécanismes** — `turn_plan` reste déclenché et `continuation` s'exécute : le journal
   `auto-continue` (`prompt.ts:1916`) reste émis, au moins une fois, sur le scénario.

Commande de mesure : `cd packages/opencode && bun test --timeout 30000 ./test/session/single-provider-call.test.ts`.
Valeurs attendues : `provider_calls <= 2`, `billed_tokens <= baseline`, `cache_read >= baseline`,
`auto_continue_events >= 1`. Comparaison à `../BASELINE.md`.

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/single-provider-call.test.ts`.

Commande : `bun test --timeout 30000 ./test/session/single-provider-call.test.ts`.

Cas, avec critère observable :

1. **Un seul `streamText` pour N rounds** — scénario scripté à 5 tool-calls enchaînés : compter les
   invocations provider (spy sur `llm.stream` ou compteur d'événements `step-start` par appel) ; succès :
   `provider_calls <= 2`.
2. **Surface d'événements préservée** — le stream du tour produit 5 paires `step-start`/`step-finish`
   ordonnées ; succès : `count(step-start) === count(step-finish) === 5` et index croissants (`ai-sdk.ts:80`).
3. **Budget de steps** — avec `agent.steps = 3` et `n = 8`, le tour s'arrête à 3 steps ; succès :
   `steps_consumed === 3` (pas de dépassement).
4. **Test par mutation** — forcer `stopWhen = stepCountIs(1)` doit **reproduire** 5 appels provider (le
   test 1 échoue) ⇒ prouve que le levier est bien `stopWhen`, pas un effet de bord.
5. **Turn-plan / continuation** — sur le scénario, `auto-continue` est journalisé au moins une fois ;
   succès : `auto_continue_events >= 1`.

Régression : relancer `test/session/llm.test.ts`, `llm-native.test.ts`, `processor-effect.test.ts`,
`prompt.test.ts`, et `src/session/step-limit.test.ts`, `src/session/turn-plan.test.ts`,
`src/session/continuation.test.ts`.

## 9. Effort

`L` — le patch tient en quelques lignes, mais la preuve « mécanisme par mécanisme » (turn_plan,
continuation, stall-watch, compaction, budget de steps) et la recalibration des suites de session
dominent le coût.

## 10. Verdict self-assessment

`NEEDS_REVIEW` — question à trancher par le validateur : **« appel provider » désigne-t-il les invocations
orchestrées par opencode (`streamText`) ou les requêtes HTTP au modèle ?** Le §7 mesure les invocations
orchestrées (cible `BASELINE.md:60` : 1 pour N rounds). Si le validateur entend les requêtes HTTP, le
multi-step natif ne les réduit **pas** — une boucle à N rounds d'outils exige N+1 complétions — et le
critère est inatteignable par ce correctif : la grandeur devrait être précisée avant merge. Point laissé
ouvert, non bloquant : le plafond par défaut de `n` et son nom de clé de config.
