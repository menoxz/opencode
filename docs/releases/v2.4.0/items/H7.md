# H7 — Dédupliquer les injections de contexte par tour

## 1. Problem

Un même tour d'agent réinjecte plusieurs fois le même fait — l'objectif et la DoD apparaissent
sur deux surfaces, deux capsules de réutilisation se recouvrent, et un même `AGENTS.md` est
payable deux fois — ce qui gonfle le préfixe/queue du prompt sans ajouter d'information.

## 3. Mechanism

À chaque construction de tour, `prompt.ts` remplit la liste `volatile` dans l'ordre :

1. la capsule `holdings` (prompt.ts:2331) — `<context-holdings>`, bornée à 40 entrées / 1600 chars ;
2. une pièce jointe instruction éventuelle (instruction.ts:310+, le `AGENTS.md` remonté) ;
3. le contexte goal (`goalCtx`, prompt.ts:2411) — `<task-contract>` avec objectif + DoD ;
4. la capsule `context_slots` (prompt.ts:2468) — `<context_slots>`, une ligne canonique par cible ;
5. le `<goal_reminder>` (prompt.ts:2502) — consigne de cycle de vie **seule** (pas d'objectif/DoD).

Séparément, **hors** de cette liste, la carte `<working-state>` est produite plus loin et attachée
en **queue** de la requête LLM (pas dans `volatile`) :

6. `<working-state>` — `WorkingState.current` (llm.ts:169) puis `WorkingState.attach`
   (request.ts:298) — objectif + DoD + `out_of_scope` + todo actif.

Les étapes **1 et 4** répondent à la même question (« qu'est-ce que je tiens déjà ? ») avec deux
formats ; les étapes **3 et 6** transportent le **même contrat** (objectif/DoD) sous deux formes
(dans deux zones différentes du prompt : `volatile` pour l'une, queue de messages pour l'autre).
L'étape **5** ne transporte pas le contrat : elle ne rappelle que la procédure. Le budget de
contexte paie donc des octets redondants, à chaque tour, pour une information que le modèle tient
déjà.

## 4. Proposal

**Une seule injection par fait.**

- **Objectif/DoD** : l'objectif et la DoD sont injectés **une fois** par tour. Conserver la surface
  la plus riche en information structurée — `<task-contract>` via `formatGoalContext`
  (prompt.ts:2411) — et faire que la carte `<working-state>` **cesse de re-rendre `goal`/`dod`**
  quand `<task-contract>` est déjà présent dans le tour (elle devient purement « état éphémère
  applicatif » : todo actif, statut, evidence refs), via un paramètre `includeContract` porté
  jusqu'à `render` (`working-state.ts:31`).
- **`<goal_reminder>` — non-action assumée (rectification H7-O1)** : ce bloc est **purement
  procédural** et ne duplique ni objectif ni DoD (vérifié : prompt.ts:2488-2498, aucun
  `goalState.goal`/`goalState.dod`). Il est **conservé tel quel** : il n'y a rien à en retirer, et
  le supprimer nuirait au pilotage de l'objectif sans aucun gain d'octets.
- **Point d'injection réel (corrigé, H7-O2)** : `<working-state>` n'est **pas** un élément de
  `volatile` dans `prompt.ts` — il n'existe aucune occurrence de `working-state` dans `prompt.ts`.
  La carte est produite par `WorkingState.current` (`llm.ts:169`) et attachée en queue par
  `WorkingState.attach` (`llm/request.ts:298`). En conséquence, le calcul « le contrat est-il déjà
  présent ? » doit se faire dans `prompt.ts` (qui voit `system` + `volatile`) et la décision doit
  être **transmise** à `WorkingState.current` (nouveau paramètre/flag `includeContract`), puis
  honorée par `render` (`working-state.ts:31`), qui omet les lignes `goal:`/`dod:` quand il est
  faux. `WorkingState.attach` reste inchangé.
- **Capsule de réutilisation unique** : fusionner `<context-holdings>` et `<context_slots>` en une
  seule capsule. La source retenue est le ledger de contexte (`context-ledger.ts`, plus riche :
  coverage de lignes, `observed Nx`, statut superseded) ; `holdings-capsule.ts` est supprimé et son
  rôle (lister ce qui est tenu) est absorbé.
- **`AGENTS.md` une fois** : la passe pièce-jointe (instruction.ts:310+) ne doit pas rattacher un
  fichier déjà injecté en système ; `sys.has(found)` couvre déjà ce cas (instruction.ts:329) —
  vérifier/quasiment confirmer que ce garde est bien actif pour *tous* les fichiers système et non
  seulement ceux découverts par le même chemin (c'est le point à instrumenter).

Fichiers modifiés : `session/prompt.ts` (calcul de `hasContract` et dédup des push `volatile`),
`session/working-state.ts` (signature `render` + `current` honorant `includeContract`),
`session/llm.ts` (transport de `includeContract` vers `WorkingState.current`),
`session/holdings-capsule.ts` (suppression), `session/context-ledger.ts` (en-tête unifiée),
`session/instruction.ts` (garde anti-double). `tool/shell/prompt.ts` non touché.

Code cible (≤ 15 lignes), principe de dédup sans perte :

```ts
// prompt.ts — seule surface qui voit `system` ET `volatile`
const hasContract = system.some((e) => e.includes("<task-contract")) ||
  volatile.some((e) => e.includes("<task-contract"))
// <goal_reminder> : inchangé (procédural, rien à dédupliquer, cf. §2)

// llm.ts:169 — transmettre la décision au vrai point d'injection de la carte
workingState: yield* WorkingState.current(sessionID, userID, goalDodEnabled, !hasContract),

// working-state.ts:31 — render honore la décision : pas de recopie si contrat déjà là
export function render(input: { userID: string; goal?: GoalState; todos: readonly Todo.Info[]; includeContract?: boolean }) {
  ...
  ...(input.includeContract === false ? [] : [`goal: ${quote(goal?.goal ?? "", 900)}`, `dod: ${list(goal?.dod ?? [], 2000)}`]),
```

Reste **volontairement inchangé** :

- le **contenu** de `<task-contract>` (source unique de l'objectif) ;
- le `<goal_reminder>` **entier**, consigne de cycle de vie comprise (purement procédural) ;
- les gardes `!system.some(<…>)` (mécanisme anti-double déjà en place), qui restent la première
  défense ; la dédup corrige ce que ces gardes ne couvrent pas (surfaces différentes).

## 5. Alternatives considered

1. **Supprimer `<working-state>` entièrement.** Écartée : la carte porte aussi le todo actif, le
   statut de contrat et les `critical_evidence_refs`, non redondants ; seule sa copie de
   `goal`/`dod` est en double.
2. **Garder les deux capsules et se contenter d'en baisser les plafonds.** Écartée : réduit le coût
   sans supprimer le recouvrement ; deux formats pour un même fait restent un piège de cohérence.
3. **Dédupliquer par hachage des blocs *a posteriori* dans `volatile`.** Écartée : aveugle (deux
   blocs différents par la forme mais identiques par le sens survivront ; un bloc légitime répété
   deux fois pour une raison serait supprimé) et non testable finement. On préfère une dédup par
   **origine** (le fait), pas par **octets**.

## 6. Risks

- **Régression tests existants** (fichiers réels, directement touchés par le patch) :
  - `packages/opencode/src/session/holdings-capsule.test.ts` — teste `contextHoldingsCapsule`, que
    §4 **supprime** : il cassera au build. Régression la plus certaine ; migrer ses cas vers
    `context-ledger.test.ts` **avant** de supprimer le module.
  - `packages/opencode/src/session/context-ledger.test.ts` — asserte `contextCapsule`/`buildCapsule`
    (≈ l.197, 209, 226), que §4 modifie.
  - `packages/opencode/test/session/working-state.test.ts`,
    `packages/opencode/test/session/working-state-runtime.test.ts`,
    `packages/opencode/test/session/working-state-goal-dod.test.ts` — la signature `render` change.
  - `packages/opencode/src/session/goal-context.test.ts` (formatage du contrat) et
    `packages/opencode/test/session/instruction.test.ts` (garde anti-double `AGENTS.md`).
  - `packages/opencode/test/tool/goal-contract.test.ts`, `test/tool/registry.test.ts`,
    `test/tool/parameters.test.ts` — surfaces de prompt inchangées, à relancer.
  - `packages/opencode/src/session/prompt-budget.test.ts` — **non modifié** (la mesure octets est
    déportée dans `context-dedup.test.ts`, cf. §7/O3) ; il doit continuer à passer à valeur
    constante.
- **Perte d'information si l'on déduplique trop** — risque central. Mitigation : la dédup porte sur
  des **faits** (objectif, DoD, listes de tenus) dont l'unicité est *prouvée* par un test (§8) ; on
  ne retire jamais la **dernière** copie d'un fait. Interdiction de supprimer la consigne de cycle
  de vie du `<goal_reminder>`.
- **Coût tokens/latence ajouté** : négatif (c'est un gain). Gain attendu ≈ octets de la 2ᵉ copie
  de l'objectif/DoD + 1 capsule (`≤ 1600` chars) par tour ; à confirmer par la mesure, pas affirmé
  ici.
- **Sécurité** : aucune. Pas de contournement de permission (les surfaces sont des chaînes de
  prompt, pas des décisions de garde). À surveiller : ne pas supprimer un garde `!system.some(<…>)`
  en croyant dédupliquer.

## 7. Acceptance (critère monotone)

Critère **absolu et monotone**, mesuré sur un **tour assemblé** par le nouveau test (l'instrument
`prompt-budget.test.ts` ne mesure que `PROMPT_CORE` et le catalogue de skills : il n'assemble
aucun tour, il n'est donc pas l'instrument de ce critère — verdict H7-O3) :

1. **Octets** : sur le tour de référence assemblé par `context-dedup.test.ts`, le `(préfixe +
   queue)` **baisse** des octets des copies redondantes supprimées — mesuré par différence entre
   `bytes_baseline` consignée et `bytes_after` mesurée (jamais un ratio dont le dénominateur serait
   ce que le patch fait baisser ; on compare deux **valeurs absolues**).
2. **Sans perte** : le même test prouve que **l'objectif et la DoD restent présents exactement une
   fois** dans le turn assemblé (compte d'occurrences = 1 pour chacun).

Commande de mesure : `bun test --timeout 30000 ./test/session/context-dedup.test.ts`. Valeur
attendue : `bytes_after < bytes_baseline` sur le tour de référence, et `count(goal) === 1`,
`count(dod) === 1`. `bytes_baseline` est figée dans le même changeset que le patch (valeur relevée
avant application, consignée dans le test). Comparaison à `../BASELINE.md`. Le test d'unicité est
**obligatoire** : un gain d'octets sans preuve de non-perte ne satisfait pas le critère.
