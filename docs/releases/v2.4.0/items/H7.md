# H7 — Dédupliquer les injections de contexte par tour

## 1. Problem

Un même tour d'agent réinjecte plusieurs fois le même fait — l'objectif et la DoD apparaissent
sur plusieurs surfaces, deux capsules de réutilisation se recouvrent, et un même `AGENTS.md` est
payable deux fois — ce qui gonfle le préfixe/queue du prompt sans ajouter d'information.

## 3. Mechanism

À chaque construction de tour (`prompt.ts`), la liste `volatile` reçoit, dans l'ordre :

1. la capsule `holdings` (prompt.ts:2331) — `<context-holdings>`, bornée à 40 entrées / 1600 chars ;
2. une pièce jointe instruction éventuelle (instruction.ts:310+, le `AGENTS.md` remonté) ;
3. le contexte goal (`goalCtx`, prompt.ts:2411) — `<task-contract>` avec objectif + DoD ;
4. la capsule `context_slots` (prompt.ts:2468) — `<context_slots>`, une ligne canonique par cible ;
5. le `<goal_reminder>` (prompt.ts:2488) — objectif courant et consigne de cycle de vie ;
6. le `<working-state>` (working-state.ts:53) — objectif + DoD + `out_of_scope` + todo actif.

Les étapes **1 et 4** répondent à la même question (« qu'est-ce que je tiens déjà ? ») avec deux
formats ; les étapes **3, 5 et 6** transportent le même contrat (objectif/DoD) sous trois formes.
Le budget de contexte paie donc des octets redondants, à chaque tour, pour une information que le
modèle tient déjà.

## 4. Proposal

**Une seule injection par fait.**

- **Objectif/DoD** : l'objectif est injecté **une fois** par tour. Conserver la surface la plus
  riche en information structurée — `<task-contract>` via `formatGoalContext` (prompt.ts:2411) —
  et faire que `<goal_reminder>` **ne réinjecte plus l'objectif** : il ne garde que la consigne de
  cycle de vie (« compare le dernier message…, complète/édite ») et **pointe** vers le
  `<task-contract>` déjà présent au lieu de le recopier.
- **La carte `<working-state>`** cesse de re-rendre `goal`/`dod` quand `<task-contract>` est déjà
  présent dans le tour (elle devient purement « état éphémère applicatif » : todo actif, statut,
  evidence refs), via un paramètre `render({ …, includeContract })`.
- **Capsule de réutilisation unique** : fusionner `<context-holdings>` et `<context_slots>` en une
  seule capsule. La source retenue est le ledger de contexte (`context-ledger.ts`, plus riche :
  coverage de lignes, `observed Nx`, statut superseded) ; `holdings-capsule.ts` est supprimé et son
  rôle (lister ce qui est tenu) est absorbé.
- **`AGENTS.md` une fois** : la passe pièce-jointe (instruction.ts:310+) ne doit pas rattacher un
  fichier déjà injecté en système ; `sys.has(found)` couvre déjà ce cas (instruction.ts:329) —
  vérifier/quasiment confirmer que ce garde est bien actif pour *tous* les fichiers système et non
  seulement ceux découverts par le même chemin (c'est le point à instrumenter).

Fichiers modifiés : `session/prompt.ts` (dédup des push `volatile`), `session/working-state.ts`
(signature `render`), `session/holdings-capsule.ts` (suppression), `session/context-ledger.ts`
(en-tête unifiée), `session/instruction.ts` (garde anti-double), `tool/shell/prompt.ts` non touché.

Code cible (≤ 15 lignes), principe de dédup sans perte :

```ts
// prompt.ts, après avoir calculé `system`/`volatile`
const hasContract = system.some((e) => e.includes("<task-contract")) ||
  volatile.some((e) => e.includes("<task-contract"))
// goal_reminder : consigne seule si le contrat est déjà là
if (goalActive && !hasContract && !system.some((e) => e.includes("<goal_reminder"))) {
  volatile.push(goalReminderAdvisoryOnly(goalState)) // pas de recopie de goal/dod
}
// working-state : carte sans contrat si déjà injecté
workingStateRender({ userID, goal, todos, includeContract: !hasContract })
```

Reste **volontairement inchangé** :

- le **contenu** de `<task-contract>` (source unique de l'objectif) ;
- le `<goal_reminder>` comme **incitation** de cycle de vie (sa disparition totale nuirait au
  pilotage de l'objectif ; on retire le texte, pas la fonction) ;
- les gardes `!system.some(<…>)` (mécanisme anti-double déjà en place), qui restent la première
  défense ; la dédup corrige ce que ces gardes ne couvrent pas (surfaces différentes).

## 5. Alternatives considered

1. **Supprimer `<working-state>` entièrement.** Écartée : la carte porte aussi le todo actif, le
   statut de contrat et les `critical_evidence_refs`, non redondants ; seule sa copie de
   `goal`/`dod` est en double.
2. **Garder les deux capsules et se contenter d'en baisser les plafonds.** Écartée : réduit le coût
   sans supprimer le recouvrement ; deux formats pour un même fait restent un piège de cohérence.
3. **Dédupliquer par hachage des blocs *a posteriori* dans `volatile`.** Écartée : aveugle
   (deux blocs différents par la forme mais identiques par le sens survivront ; un bloc légitime
   répété deux fois pour une raison serait supprimé) et non testable finement. On préfère une dédup
   par **origine** (le fait), pas par **octets**.

## 6. Risks

- **Régression tests existants** (fichiers réels) :
  `packages/opencode/src/session/prompt-budget.test.ts` (mesure de budget — **va changer de valeur
  attendue**, à recalibrer dans le même changeset),
  `packages/opencode/test/tool/goal-contract.test.ts`,
  `packages/opencode/test/tool/registry.test.ts`,
  `packages/opencode/test/tool/parameters.test.ts`,
  `packages/opencode/test/session/*` (injection d'instructions : à relancer).
- **Perte d'information si l'on déduplique trop** — risque central. Mitigation : la dédup porte sur
  des **faits** (objectif, DoD, listes de tenus) dont l'unicité est *prouvée* par un test (§8) ; on
  ne retire jamais la **dernière** copie d'un fait. Interdiction de supprimer la consigne de cycle
  de vie du `<goal_reminder>`.
- **Coût tokens/latence ajouté** : négatif (c'est un gain). Gain attendu ≈ octets de 2 copies de
  l'objectif/DoD + 1 capsule (`≤ 1600` chars) par tour ; à confirmer par la mesure, pas affirmé ici.
- **Sécurité** : aucune. Pas de contournement de permission (les surfaces sont des chaînes de
  prompt, pas des décisions de garde). À surveiller : ne pas supprimer un garde `!system.some(<…>)`
  en croyant dédupliquer.

## 7. Acceptance (critère monotone)

Critère **absolu et monotone** :

1. **Octets** : sur le tour de référence de `prompt-budget.test.ts`
   (`packages/opencode/src/session/prompt-budget.test.ts`), le `(préfixe + queue)` **baisse** des
   octets des copies redondantes supprimées — mesuré par différence entre la valeur de référence
   consignée et la valeur mesurée (jamais un ratio dont le dénominateur serait ce que le patch fait
   baisser ; on compare deux **valeurs absolues**, baseline et après).
2. **Sans perte** : un test prouve que **l'objectif et la DoD restent présents exactement une fois**
   dans le turn assemblé (compte d'occurrences = 1 pour chacun).

Commande de mesure : `bun test --timeout 30000 ./src/session/prompt-budget.test.ts`. Valeur
attendue : `bytes_after < bytes_baseline` sur le tour de référence, et `count(goal) === 1`,
`count(dod) === 1`. Comparaison à `../BASELINE.md`. Le test d'unicité est **obligatoire** : un gain
d'octets sans preuve de non-perte ne satisfait pas le critère.

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/context-dedup.test.ts`.

Commande : `bun test --timeout 30000 ./test/session/context-dedup.test.ts`.

Cas, avec critère observable :

1. **Unicité de l'objectif** — tour de référence : `countOccurrences(turn, "<task-contract>")` ≥ 1
   mais la **chaîne objectif** n'apparaît qu'une fois dans `préfixe + queue` (succès : `=== 1`).
2. **Unicité de la DoD** — idem pour la liste DoD (succès : `=== 1`).
3. **Test par mutation (garde de dédup)** — forcer `includeContract=false` alors que
   `<task-contract>` **est** présent doit **ne pas** produire de seconde copie ; et forcer
   `includeContract=true` sans `<task-contract>` doit **produire** la copie (succès : présence
   exactement une fois dans les deux cas) ⇒ prouve que le garde marche dans les deux sens.
4. **Capsule unique** — le turn assemblé contient **une seule** des deux en-têtes
   (`<context-holdings>` **xor** `<context_slots>`) (succès : somme = 1).
5. **`AGENTS.md` unique** — un fichier d'instruction injecté en système (instruction.ts:264+) n'est
   **pas** réattaché par la remontée (instruction.ts:310+) sur la lecture d'un fichier voisin
   (succès : `countOccurrences(turn, instructionPath) === 1`).
6. **Référence `prompt-budget`** — `./src/session/prompt-budget.test.ts` recalculé : `bytes_after <
   bytes_baseline`, valeur plancher recalibrée explicitement dans le même changeset.

Régression : `test/tool/goal-contract.test.ts`, `test/tool/registry.test.ts`,
`test/tool/parameters.test.ts`, `test/session/*` (injection d'instructions).

## 9. Effort

`S` — changements localisés à des points de `push` et à deux signatures de rendu ; pas de nouveau
sous-système. Le coût réel est dans la recalibration de `prompt-budget.test.ts` et la preuve
d'unicité, pas dans le patch.

## 10. Verdict self-assessment

`NEEDS_REVIEW` — une question à trancher par le validateur : **où s'arrête la dédup ?** La fiche
choisit « un objectif une fois, capsule unique, pas de double `AGENTS.md` », mais laisse ouverte la

fois » est sans ambiguïté ; la valeur plancher de `prompt-budget.test.ts` devra être figée en revue
