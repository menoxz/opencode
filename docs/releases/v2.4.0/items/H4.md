# H4 — Un seul spawn git par étape (et non deux)

## 1. Problem

Une étape d'agent déclenche deux captures d'instantané `git` distinctes (une au pré-appel,
une au `step-finish`) alors qu'une seule suffit : un tour à N étapes paie ~2N captures
`git write-tree` là où N+1 suffiraient, pour un diff identique.

## 2. Evidence

Pré-appel avant le flux LLM — `packages/opencode/src/session/processor.ts:141-144` :

```
      // Pre-capture snapshot before the LLM stream starts. The AI SDK
      // may execute tools internally before emitting start-step events,
      // so capturing inside the event handler can be too late.
      const initialSnapshot = yield* trackSnapshot
```

`trackSnapshot` est la capture nue (`snapshot.track()`) — `processor.ts:131-138` :

```

      Effect.catchCause((cause) =>
        Effect.sync(() => {

          return undefined

```

Le hash du pré-appel est rangé dans le contexte du processeur — `processor.ts:144-151` :

```
      const initialSnapshot = yield* trackSnapshot
      const ctx: ProcessorContext = {
        ...
        snapshot: initialSnapshot,
```

Seconde capture au `step-finish` — `processor.ts:706-708` :

```

```

Puis le patch, qui relance `git` une troisième fois — `processor.ts:742-744` :

```

              const patchStart = Date.now()

```

Chaque `track()` lance un `git write-tree` — `packages/opencode/src/snapshot/index.ts:319-322` :

```

                yield* add()

```

Chaque `patch()` lance un `git diff --cached` — `snapshot/index.ts:333-335` :

Les deux captures sont sérialisées par un sémaphore **monoslot** (une seule à la fois, clé =
gitdir/worktree) — `snapshot/index.ts:73-82` :

```

Le service expose la capture, le patch et le revert comme trois opérations séparées —
`snapshot/index.ts:56-59` :

```

  readonly patch: (hash: string) => Effect.Effect<Patch>
  readonly restore: (snapshot: string) => Effect.Effect<void>

BASELINE mesurée (reprise, non re-mesurée) : `git status --porcelain=v1` **75,7 ms**,
`git rev-parse HEAD` **42,1 ms** ⇒ ~**118 ms** par étape pour les deux spawns de référence.

`INFERE:` le pré-appel et le `step-finish` calculent le même état de l'arbre utile, donc l'un
des deux `write-tree` est redondant. Méthode de vérification : instrumenter le spawner git de
`snapshot/index.ts` (compteur) et compter les invocations sur un tour à N=3 étapes ; attendu
baseline ≈ 2 captures + 3 patches, attendu après patch ≈ 1 capture + 3 patches.

## 3. Mechanism

Chemin d'exécution de bout en bout qui produit le coût :

1. Début d'étape : `create` prend `initialSnapshot = yield* trackSnapshot`
   (`processor.ts:144`) → `snapshot.track()` → `git … write-tree`
   (`snapshot/index.ts:321`), sérialisé par le sémaphore (`snapshot/index.ts:73-82`). Le hash
   est conservé dans `ctx.snapshot` (`processor.ts:151`).
2. Le flux LLM s'exécute ; les outils mutateurs écrivent sur le worktree.
3. `step-finish` : `completedSnapshot = yield* trackSnapshot` (`processor.ts:708`) → **second**
   `git … write-tree`, une capture supplémentaire pour le même arbre.
4. Puis `snapshot.patch(ctx.snapshot)` (`processor.ts:744`) → `git … diff --cached …`
   (`snapshot/index.ts:334`) pour produire la liste des fichiers modifiés.
5. `ctx.snapshot = undefined` (`processor.ts:759`) : la base est jetée.
6. L'étape suivante repart en 1 ⇒ **deux** captures par étape. `create` est ré-invoqué à
   chaque itération de `while (true)` (`prompt.ts:1758`, `step++` `:1933`, appel
   `processor.create` `:2103`), donc `ctx` est **local à l'étape** et ne peut porter aucun
   état inter-étapes.

Le §4 conserve la capture de fin d'étape *k* comme base de l'étape *k+1* via un porteur **de
tour** (§4) et supprime le pré-appel pour les étapes ≥ 2.

## 4. Proposal

**Une seule capture par étape, réutilisée.**

Fichiers modifiés :

- `packages/opencode/src/session/prompt.ts` — **porteur d'état inter-étapes** : un objet
  mutable `const carried: { snapshot?: string } = {}` déclaré **avant** `while (true)`
  (`prompt.ts:1758`), à côté de `idleContinues` (`:1755`) et `autoContinueInstruction` (`:1756`),
  passé dans l'`Input` de `processor.create` (`prompt.ts:2103-2108`).
- `packages/opencode/src/session/processor.ts` — `Input` reçoit `carrier?: { snapshot?: string }`
  (`processor.ts:75-79`) : l'entrée de `create` lit `input.carrier?.snapshot` comme base, et le
  `step-finish` **écrit** le hash de fin d'étape dans `input.carrier` ; `ctx.snapshot` n'est plus
  remis à `undefined` (`processor.ts:759`).

`Input` (`processor.ts:75`) et `Handle` (`processor.ts:57-73`) sont des types **locaux** à
`processor.ts`, non exportés. `Handle` n'expose aujourd'hui que `message`, `updateToolCall`,
`completeToolCall` et `process` — **pas** de `snapshot` : le porteur est donc un objet mutable
passé en `Input` (aucune modification de `Handle` requise), et non une valeur rendue par `create`.

Code cible (≤ 15 lignes), ancré sur le porteur réel :

```ts
// prompt.ts — AVANT while (true) (prompt.ts:1758), à côté de `idleContinues` (:1755)
const carried: { snapshot?: string } = {}

// prompt.ts — appel réel de create (prompt.ts:2103-2108)
const handle = yield* processor.create({ assistantMessage: msg, sessionID, model, carrier: carried })

// processor.ts — Input (processor.ts:75-79)
type Input = { assistantMessage: MessageV2.Assistant; sessionID: SessionID; model: Provider.Model; carrier?: { snapshot?: string } }
// entrée de create : ne capturer qu'une fois par étape
const initialSnapshot = input.carrier?.snapshot ?? (yield* trackSnapshot)
// ctx.snapshot = initialSnapshot
// step-finish : une capture, base conservée ET publiée dans le porteur
const completedSnapshot = yield* trackSnapshot
if (input.carrier) input.carrier.snapshot = completedSnapshot
// ctx.snapshot n'est PAS remis à undefined : base de l'étape suivante
```

**Le porteur est indispensable** : `create` est ré-invoqué à chaque itération de `while (true)`
(`prompt.ts:1758`, `step++` `:1933`, appel `:2103`) ⇒ `ctx` (et `ProcessorContext`,
`processor.ts:93-101`) est local à l'étape, et `Handle` ne transporte aucune valeur de retour
d'étape. Le porteur mutable passé en `Input` est la voie minimale ; un état de session
(`InstanceState`) marcherait aussi mais serait surdimensionné ici.

Reste **volontairement inchangé** :

- `snapshot.patch()` au `step-finish` (`processor.ts:742-744`) et la part `Patch` persistée :
  c'est la donnée du diff et du revert, pas une capture redondante ;
- le sémaphore monoslot (`snapshot/index.ts:73-82`) : il reste nécessaire dès qu'une capture
  et un patch peuvent se chevaucher ;
- `snapshot.revert()` (`snapshot/index.ts:59`) et le flux de revert/undo : le correctif change
  *combien de fois* on capture, jamais *ce qu'on capture* (le hash reste un `write-tree` sur le
  même `gitdir`/`worktree`).

## 5. Alternatives considered

1. **Supprimer purement le pré-appel, sans filet.** Écartée : la première étape a besoin d'une
   base *avant* ses mutations ; sans pré-appel, le patch de l'étape 1 n'a pas de `from` et le
   diff serait vide ou incorrect.
2. **Supprimer le `step-finish` et ne garder que le pré-appel.** Écartée : c'est précisément le
   hash de fin d'étape qu'exigent la part `step-finish` (`processor.ts:734`,
   `snapshot: completedSnapshot`) et le patch ; l'attribution du diff à l'étape serait perdue.
3. **Dédupliquer dans `snapshot.track()` (mémoïser le dernier hash dans le service).** Écartée :
   `track()` est correctement un appel *pur* côté service (le test `snapshot.test.ts:209` attend
   `track()` reproductible) ; la redondance est un défaut du **caller** (`processor.ts`), pas du
   service. Corriger au bon niveau évite un cache caché et des effets de bord sur `patch()`.

## 6. Risks

- **Régression tests existants** (fichiers réels à surveiller) :
  `packages/opencode/test/snapshot/snapshot.test.ts` (nombre d'appels `track`/`patch`
  observable — p. ex. `snapshot.test.ts:209` `expect(yield* snapshot.track()).toBe(before)`),
  `packages/opencode/test/session/processor-effect.test.ts`,
  `packages/opencode/test/session/snapshot-tool-race.test.ts` (course capture/outil),
  `packages/opencode/test/session/revert-compact.test.ts`,
  `packages/opencode/test/cli/tui/revert-diff.test.ts`,
  `packages/opencode/test/session/prompt.test.ts`.
- **Revert cassé — risque principal** : si la base conservée n'est pas le bon `from`,
  `snapshot.patch()` renvoie un diff sur-/sous-inclus et `snapshot.revert()`
  (`snapshot/index.ts:59`) restaure le mauvais état. Mitigation : le test de mutation (§8,
  cas 3) modifie puis annule et vérifie le contenu restauré octet pour octet ; le hash de fin
  d'étape *k* doit rester **postérieur** aux mutations de *k* — il devient la base de *k+1*,
  et `snapshot-tool-race.test.ts` couvre la course capture/outil qui doit continuer d'échouer
  en voyant l'arbre final ; le porteur de tour (§4) garantit cette postériorité.
- **Coût tokens / latence ajouté** : négatif (c'est un gain). Gain attendu ≈ 1 spawn `git` par
  étape ≈ 59 ms (moitié des ~118 ms de référence) ; borne dure : N=10 étapes ⇒ ~590 ms
  économisées. À confirmer par la mesure, pas affirmé.
- **Sécurité** : aucune. La capture ne franchit aucun gate de permission et ne lit ni
  n'exécute de contenu fourni par l'utilisateur ; à surveiller seulement de ne pas confondre
  cette capture avec le scan d'outils.

## 7. Acceptance (critère monotone)

Critère **absolu et monotone** (le dénominateur N est la taille du tour, il ne baisse pas avec
le patch) :

1. **Nombre de captures** : sur un tour à N étapes, le nombre de **captures** lancées par le
   sous-système snapshot — chaque `git write-tree` (`snapshot/index.ts:321`), soit un par
   `snapshot.track()` — est **≤ N+1** (baseline : 2N captures). Les `git diff --cached` de
   `snapshot.patch()` (`snapshot/index.ts:334`) sont **exclus** du comptage : hors périmètre,
   non supprimés par le correctif (§4). Sur N=3 : captures ≤ 4 contre 6 en baseline.
2. **Revert correct** : un test qui (a) capture, (b) modifie un fichier, (c) `patch()`,
   (d) `revert()` restaure le contenu d'origine **octet pour octet**.

Commande de mesure : `bun test --timeout 30000 ./test/session/step-git-spawn.test.ts` pour le
compteur et `bun test --timeout 30000 ./test/session/revert-after-single-capture.test.ts` pour
le revert. Valeurs attendues : `captures <= N+1` (N=3 ⇒ `<= 4`) ;
`content_after_revert === content_before`. Comparaison à `../BASELINE.md` (`git status`
75,7 ms / `git rev-parse` 42,1 ms, ~118 ms par étape).

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/step-git-spawn.test.ts`.
Commande : `bun test --timeout 30000 ./test/session/step-git-spawn.test.ts`.

Cas, avec critère observable :

1. **Compteur de captures** — tour de N=3 étapes avec un outil mutant par étape ; instrumenter
   le **spawner de `git write-tree`** dans `snapshot.track()` (`snapshot/index.ts:321`) ;
   succès : `captures <= N+1` (≤ 4).
2. **Étape sans mutation** — deux étapes dont la seconde n'écrit rien ; succès : delta de
   spawns nul pour l'étape 2 et `patch.files.length === 0`.
3. **Test par mutation (garde anti-capture redondante)** — neutraliser la réutilisation (vider
   le porteur, `carried.snapshot = undefined` après l'étape, comportement actuel) doit **faire
   remonter** `captures` à ~2N ; succès : `2N` ⇒ prouve que c'est bien la réutilisation qui
   économise, pas le compteur qui sous-compte.
4. **Revert** — `track()` → écriture d'un fichier → `patch()` → `revert()` ; succès : contenu
   restauré identique à l'original (critère §7.2). Fichier :
   `packages/opencode/test/session/revert-after-single-capture.test.ts`.

Régression : `snapshot.test.ts`, `processor-effect.test.ts`, `snapshot-tool-race.test.ts`,
`revert-compact.test.ts`, `revert-diff.test.ts`.

## 9. Effort

`L` — le point de capture est touché dans la boucle d'étapes (`processor.ts`), **et** le porteur
d'état inter-étapes exige de modifier `prompt.ts` (`Input` de `create` + `let` de tour dans la
boucle `while (true)`) : le correctif traverse deux fichiers. Il faut en outre prouver le
compteur et que `patch()`/`revert()` gardent la bonne base, ce qui exige un test dédié au delà
du simple comptage.

## 10. Verdict self-assessment

`résolu (verdict H4-O2)` — le porteur d'état inter-étapes est désormais **spécifié** : un objet
mutable `carried` déclaré avant `while (true)` (`prompt.ts:1758`, à côté de `idleContinues`
`:1755`), passé dans l'`Input` de `processor.create` (`prompt.ts:2103-2108`) et **écrit au
step-finish** ; `Handle` (`processor.ts:57-73`) ne porte aucune valeur de retour d'étape, d'où le
porteur mutable. Le snippet §4 est ancré sur ce porteur (plus aucun `ctx` inter-étapes supposé).
`create` étant instancié à chaque itération de `while (true)` (`prompt.ts:1758`), le porteur de
tour est la seule voie ; l'état de session (`InstanceState`) marcherait aussi mais serait
surdimensionné. L'option « capture paresseuse » (question initiale de cette section) reste
écartée : elle exige d'intercepter le premier tool call mutant (`settleToolCall`,
`processor.ts:169`) sans bénéfice pour le critère `≤ N+1`.
