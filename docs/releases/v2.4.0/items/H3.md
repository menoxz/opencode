# H3 — Retirer les éléments volatils du segment système mis en cache

## 1. Problem

Le segment système — celui que le provider met en cache devant tout l'historique — contient deux
éléments qui changent d'eux-mêmes : l'horodatage du jour et l'état de santé vivant des serveurs
MCP. Un seul octet qui bouge à cet endroit réinvalide le préfixe et refacture toute la conversation.

## 2. Evidence

L'horodatage est construit dans le bloc d'environnement dit « runtime » —
`packages/opencode/src/session/system.ts:136-146` :

```
          runtime: [
            `You are powered by the model named ${model.api.id}. The exact model ID is ${model.providerID}/${model.api.id}`,
            `Here is some useful information about the environment you are running in:`,
            `<env>`,
            `  Working directory: ${ctx.directory}`,
            `  Workspace root folder: ${ctx.worktree}`,
            `  Is directory a git repo: ${ctx.project.vcs === "git" ? "yes" : "no"}`,
            `  Platform: ${process.platform}`,
            `  Today's date: ${new Date().toDateString()}`,
```

(puis `` `</env>`, `` et `.join("\n")` à `:145-146`). La date est donc **dans** le bloc
`environment()`, et `new Date().toDateString()` est évalué à chaque appel.

La gravité de santé MCP est calculée à chaque step, à part du cache d'outils —
`packages/opencode/src/session/prompt.ts:2307-2314` :

```
            const mcpReadiness = mcp.readiness
              ? yield* mcp.readiness().pipe(Effect.catch(() => Effect.succeed({} as Record<string, boolean>)))
              : ({} as Record<string, boolean>)
            const unavailableLine = unavailableToolsLine(
              Object.entries(mcpReadiness)
                .filter(([, ok]) => !ok)
                .map(([name]) => name),
            )
```

Ces deux éléments sont poussés **dans `system`**, donc dans le préfixe —
`prompt.ts:2323-2324` :

```
            system.push([...instructions, env.stable, preloadedSkills, toolList, unavailableLine].filter((entry) => entry).join("\n"))
            system.push(env.runtime)
```

Le commentaire du code dit explicitement ce que ce segment ne doit pas contenir —
`prompt.ts:2258-2264` :

```
            const system: string[] = []
            // Rebuilt from live harness state on every step: the runtime capsule, the
            // work plan, the relevant skills, the task contract, the environment and
            // allocation capsules, and the objective reminder. They must not enter the
            // system segment, which providers cache in front of the whole history — one
            // byte of variation there re-bills the conversation. They are appended
            // after the history instead (see provider/transform.ts for the anchor).
```

Or c'est précisément `env.runtime` (qui porte la date) et `unavailableLine` (qui porte l'état MCP)
qui sont poussés dans `system`, non dans `volatile`. Le segment `volatile` existe déjà et est
**volontairement ajouté après l'historique** — `prompt.ts:2552-2568` :

```
            const injected = [...volatile, ...stepOneTail].filter((entry) => entry.trim())
            const injectedMessage = injected.length ? injected.join("\n\n") : undefined
```
```
              messages: [
                ...modelMsgs,
                ...(injectedMessage ? [{ role: "user" as const, content: PromptMethodology.wrapInjectedGuidance(injectedMessage)! }] : []),
```

Côté provider, le breakpoint qui ferme le préfixe stable est « un octet près » —
`packages/opencode/src/provider/transform.ts:359-366` :

```
// The breakpoint budget is four per request. Injected guidance is rebuilt every
// step and never replayed, so it is trimmed once: one breakpoint closes the stable
// head (tools and the whole system segment), one is an anchored high-water mark at
// the end of the previous turn, and two cover the newest reusable messages so a
// multi-step turn reuses the step it just produced. The anchor only moves when a
// new turn starts; a pair of sliding breakpoints alone never serves the same prefix
// twice, which is why the body of the conversation was paid for at full price at
// every step.
```

L'invariant « le préfixe mis en cache ne bouge pas quand seule la queue volatile change » est déjà
encodé comme test, mais **au niveau de `ProviderTransform`**, pas au niveau de l'assemblage du
segment système — `packages/opencode/test/provider/cache-anchor.test.ts:103-114` :

```
  test("keeps every cached byte of the previous request identical when only the volatile tail changes", () => {
    const history: ModelMessage[] = [head, ...turn(1), ...turn(2), { role: "user", content: "request 3" }]
    const first: ModelMessage[] = [...history, injected("slots at step 1"), injected("card at step 1")]
    const second: ModelMessage[] = [...history, ...turn(3).slice(1), injected("slots at step 2"), injected("card at step 2")]
    const deepest = Math.max(...breakpoints(first))
    const one = transform(first)
    const two = transform(second)
    expect(sharedPrefix(one, two)).toBeGreaterThan(deepest)
    expect(JSON.stringify(one.slice(0, deepest + 1))).toBe(JSON.stringify(two.slice(0, deepest + 1)))
  })
```

Ce test ne couvre **pas** le défaut : il injecte une queue volatile déjà séparée ; il ne prouve pas
que l'assemblage amont ne met pas de contenu volatil **dans** le segment système. Côté observation,
`packages/opencode/test/session/cache-prefix.test.ts:113` pin déjà que **le premier changement est
attribué à `system`** quand le système change réellement (`firstChangedSection: "system"`) : c'est
le signal exact que la date et la ligne MCP déclenchent à tort.

BASELINE (reprise, non re-mesurée) : typecheck exit 0 ; suite ciblée
`goal-contract`/`registry`/`parameters` = 86 pass / 8 fail préexistants. Les chemins
`cache-anchor.test.ts`, `cache-prefix.test.ts`, `system.test.ts`,
`src/session/unavailable-tools.test.ts` existent réellement (vérifié).

`INFERE:` la ligne `Today's date` ne change qu'au franchissement de minuit (granularité jour) et
la ligne MCP ne change qu'à une bascule de santé ; ces deux événements ne surviennent pas à chaque
tour. L'invalidation est donc **intermittente et sournoise** : elle se produit exactement quand une
session longue traverse minuit ou qu'un serveur MCP flappe, ce qui rend le coût difficile à
attribuer à l'œil. Méthode de confirmation : instrumenter `provider/transform.ts` pour journaliser
un hash du segment système par step (ou lire `firstChangedSection` du `CachePrefix`) et corréler
une bascule `system` avec un `cached_tokens` qui retombe — à exécuter dans le test du §8.

## 3. Mechanism

Chemin d'exécution de bout en bout, à chaque step d'un même tour :

1. `session/system.ts` — `environment()` fabrique `env.runtime`, qui **contient**
   `` `Today's date: ${new Date().toDateString()}` `` (`system.ts:144`) et `env.stable = ""`
   (`system.ts:149`).
2. `session/prompt.ts` — `mcp.readiness()` est lu en direct (`prompt.ts:2307-2309`) et transformé
   en `unavailableLine` (`:2310-2314`).
3. `prompt.ts:2323-2324` pousse dans `system` : `[instructions, env.stable, preloadedSkills,
   toolList, unavailableLine]` **et** `env.runtime`. Les deux éléments volatils atterrissent donc
   dans le segment caché.
4. Le provider place le breakpoint de cache « à la fin du segment système » (`transform.ts:361`) :
   toute variation d'un octet dans `system` déplace ce breakpoint et **réinvalide le préfixe**.
5. Au tour suivant avec la même session : si une journée a été franchie (date) ou si un serveur MCP
   a basculé (readiness), le `system` diffère d'octets ⇒ `firstChangedSection === "system"` ⇒ le
   préfixe est refacturé au tarif plein.

Le §4 corrige l'étape 3 : les deux éléments vivants quittent `system` pour `volatile`
(l'étape 4 et l'étape 5 cessent alors de se déclencher pour ces raisons).

## 4. Proposal

**Sortir du segment système tout ce qui est vivant, et l'ajouter à `volatile` (déjà hors préfixe).**

- **`packages/opencode/src/session/system.ts`** — `environment()` cesse de mettre la date dans
  `runtime` ; elle est exposée dans un **champ volatile** distinct. Forme retenue : ajouter une clé
  `volatile` au retour (à côté de `runtime` et `stable`), contenant la seule ligne de date. Le bloc
  `<env>` de `runtime` reste intact mais **ne contient plus la ligne de date**.
- **`packages/opencode/src/session/prompt.ts`** — deux déplacements :
  - retirer `unavailableLine` du `system.push` (`:2323`) et le pousser dans `volatile`
    (après la capsule `holdings`, `:2332`) ;
  - pousser `env.volatile` dans `volatile` (et non dans `system`).
  - Mettre à jour les deux carriers d'information qui reflètent la composition :
    `contextSummary.add("env", …, [env.stable, env.runtime], 0)` (`:2241`) et la section
    `contextSections` (`:2360-2362`), pour qu'ils restent cohérents avec le nouveau découpage
    (information présente, mais comptée dans la partie volatile).

Code cible (≤ 15 lignes), principe — la date change de camp, une seule fois :

```ts
// system.ts — environment() : la date quitte le bloc cacheable
return {
  runtime: [
    `You are powered by the model named ${model.api.id}. The exact model ID is ${model.providerID}/${model.api.id}`,
    `<env>`, /* … lignes stables … */ `  Platform: ${process.platform}`, `</env>`,
  ].join("\n"),
  stable: "",
  volatile: `Today's date: ${new Date().toDateString()}`,
}
```

```ts
// prompt.ts — le vivant va dans volatile, pas dans system
system.push([...instructions, env.stable, preloadedSkills, toolList].filter((entry) => entry).join("\n"))
system.push(env.runtime)
if (env.volatile) volatile.push(env.volatile)
if (unavailableLine) volatile.push(unavailableLine)
```

Reste **volontairement inchangé** :

- `env.runtime` et `instructions` restent dans `system` : ils sont **stables** tant qu'aucun fichier
  d'instruction ne change, et c'est exactement ce que le préfixe doit cacher ;
- le **contenu** de la ligne de date et de `unavailableToolsLine` (`unavailable-tools.ts:16`) :
  aucune perte d'information, seule la **position** change ;
- `applyCaching` (`transform.ts:367-421`) et sa garde : hors périmètre (H2 s'en occupe) ; H3 rend
  simplement la garde efficace en ne faisant pas bouger `system`.

## 5. Alternatives considered

1. **Laisser la date dans `system` mais arrondir à la semaine.** Écartée : réduit la fréquence sans
   supprimer la cause ; une session de plusieurs jours paierait encore une invalidation, et cela
   dégrade l'information (« aujourd'hui » faux). Le déplacement est strictement meilleur.
2. **Figer la date au démarrage de session (calculée une fois).** Écartée : une session longue
   annoncerait une date fausse, sans que le modèle puisse le savoir. On préfère la vérité en
   position volatile.
3. **Ne retirer que la ligne MCP, garder la date.** Écartée : deux causes d'invalidation pour un
   même correctif ; traiter les deux est le même travail et le critère du BACKLOG les nomme tous les
   deux.
4. **Réinsérer la date dans `instructions` (déjà en système).** Écartée : ne fait que déplacer le
   défaut vers un autre élément du même segment caché.

## 6. Risks

- **Régression tests existants** (fichiers réels vérifiés) :
  `packages/opencode/test/session/cache-prefix.test.ts` (observe la composition ; l'ordre
  `system`/`messages` change),
  `packages/opencode/test/provider/cache-anchor.test.ts` (pin le breakpoint du segment système —
  doit rester vrai, le segment existe toujours),
  `packages/opencode/test/session/system.test.ts` (n'assert pas la date aujourd'hui, mais est le
  point naturel où un futur test la cherchera),
  `packages/opencode/src/session/unavailable-tools.test.ts` (unitaire du constructeur de ligne —
  **ne doit pas changer**, le déplacement est en amont),
  `packages/opencode/src/session/environment.test.ts` (module `environment` **distinct** ; à ne pas
  confondre, à relancer sans modification),
  `packages/opencode/src/session/prompt-budget.test.ts` et
  `packages/opencode/test/session/context-budget.test.ts` (la répartition des octets
  système/volatile bouge ; valeurs attendues à recalibrer dans le même changeset).
- **Perte d'information** — risque central. Mitigation : la date et la ligne MCP sont **déplacées**,
  jamais supprimées ; le test du §8 prouve leur présence exactement une fois (dans `volatile`).
- **Coût tokens / latence ajouté** : nul en nombre d'octets (déplacement pur) ; le gain est la
  **suppression d'invalidations** de préfixe, à mesurer au §8 et non affirmé ici.
- **Sécurité** : aucune. On déplace une chaîne de prompt ; aucun gate de permission en jeu. À
  surveiller : ne pas déplacer par erreur `instructions` (qui doit rester caché) — la garde du §8
  (test 3, « un changement d'instruction change bien `system` ») l'empêche.

## 7. Acceptance (critère monotone)

Critère **absolu et monotone** (comparaison d'octets et comptes de différence, jamais un ratio dont
le dénominateur serait la grandeur que le patch fait baisser) :

1. **Octet-identique** : sur un workspace fixe et un jeu d'instructions fixe, assembler le segment
   `system` à deux steps successifs — une fois avec `mcp.readiness()` tout-ok, une fois avec un
   serveur déclaré indisponible — et comparer les **octets** du `system` assemblé.
   Attendu : `diff_bytes(system_A, system_B) === 0` (égalité stricte, pas un seuil).
   Référence : sans le patch, `diff_bytes > 0` (la ligne `<unavailable_tools>` apparaît), et la
   date suffit à rendre `diff_bytes > 0` à un franchissement de jour.
2. **Sans perte** : dans le tour assemblé, `count(<unavailable_tools>) === 1` quand un serveur est
   indisponible et `count(Today's date…) === 1` — l'information reste émise, exactement une fois,
   désormais dans `volatile`.
3. **Garde non trop large** : modifier un fichier d'instruction (l'`AGENTS.md` du workspace) entre
   les deux steps ⇒ `diff_bytes(system_A, system_B) > 0` — le patch ne rend pas le segment
   insensible à ce qui **doit** l'invalider.

Commande de mesure : `bun test --timeout 30000 ./test/session/system-prefix-stability.test.ts`.
Valeurs attendues : `diff_bytes === 0` (critère 1), `count === 1` (critère 2), `diff_bytes > 0`
(critère 3). Comparaison à `../BASELINE.md`.

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/system-prefix-stability.test.ts`.

Commande : `bun test --timeout 30000 ./test/session/system-prefix-stability.test.ts`.

Cas, avec critère observable :

1. **Octets stables (test par mutation, sens 1)** — assembler `system` deux fois avec la **même**
   readiness MCP : succès = `Buffer.compare(bufA, bufB) === 0`. Simuler `readiness` tout-ok puis
   `{ memory: false }` : succès = **toujours** `Buffer.compare === 0` (c'est le cœur du critère §7.1).
2. **Test par mutation (sens 2, prouver que le garde marche)** — réinjecter volontairement la ligne
   de date et/ou `unavailableLine` dans le `system` (neutraliser le correctif) : succès =
   `Buffer.compare !== 0` ⇒ le test **échoue** si le correctif est retiré. Le test prouve ainsi que
   l'invariant est actif, pas seulement qu'il est présent.
3. **Ré-invalidation légitime** — écrire/modifier un `AGENTS.md` du tmpdir entre deux assemblées :
   succès = `Buffer.compare !== 0` (le segment système reste sensible aux instructions).
4. **Sans perte** — dans le tour assemblé (readiness dégradée) : succès =
   `countOccurrences(turn, "<unavailable_tools>") === 1` et
   `countOccurrences(turn, "Today's date") === 1`, tous deux dans la queue volatile.

Régression : relancer `test/provider/cache-anchor.test.ts`, `test/session/cache-prefix.test.ts`,
`test/session/system.test.ts`, `src/session/unavailable-tools.test.ts`,
`src/session/environment.test.ts`, `src/session/prompt-budget.test.ts`.
