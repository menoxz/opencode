# H5 — Mémoïser la découverte des fichiers d'instruction

## 1. Problem

À chaque étape, le moteur ré-explore le disque pour retrouver la **liste** des fichiers
d'instruction (`AGENTS.md`, `CLAUDE.md`) alors que cette liste ne change presque jamais : seuls
les **contenus** lus sont mémoïsés, pas les **chemins** découverts.

## 3. Mechanism

Chemin d'exécution de bout en bout qui produit le coût :

1. `prompt.ts:2201` appelle `instruction.system()` à chaque étape.
2. `system()` (`instruction.ts:264`) résout la config puis appelle `systemPaths()`
   (`instruction.ts:268`).
3. `systemPaths()` (`instruction.ts:260`) appelle `discoverSystemPaths()` — sans cache.
4. `discoverSystemPaths()` (`instruction.ts:193`) enchaîne `fs.existsSafe(globalFiles…)`
   (`instruction.ts:200`) puis `fs.findUp(file, ctx.directory, ctx.worktree)`
   (`instruction.ts:212`) pour chaque `instructionFiles`.
5. `findUp` (`filesystem.ts:187-212`) reconstruit la chaîne des ancêtres (`filesystem.ts:193-201`)
   puis appelle `exists` sur chaque `(dir, cible)` (`filesystem.ts:205-209`) ⇒ disque.
6. Enfin `system()` lit les contenus (`instruction.ts:277`, `Effect.forEach(…, read, {
   concurrency: 8 })`) — **seule** partie mémoïsée (`reads`, `instruction.ts:158-166`).
7. L'étape suivante repart en 1 : la liste des chemins est recalculée alors qu'elle n'a pas
   bougé.

Le §4 insère un cache au niveau de l'étape 3, invalidé par une sentinelle bon marché.

## 4. Proposal

**Mémoïser la liste des chemins découverts, invalider sur changement.**

Fichiers modifiés : `packages/opencode/src/session/instruction.ts` (un seul fichier).

- Ajouter au state (`instruction.ts:116-125`, à côté de `reads`) un champ
  `paths: { key: string; value: Set<string> } | undefined`.
- Dans `systemPaths()` (`instruction.ts:260`), construire une clé de mémoïsation et ne refaire
  `discoverSystemPaths()` que si elle a changé.
- La clé inclut : `ctx.directory`, `ctx.worktree`, `Flag.OPENCODE_DISABLE_PROJECT_CONFIG`, et
  le **mtime des répertoires** — la chaîne scannée (`ctx.directory → ctx.worktree`), le
  répertoire de config global `global.config`, le répertoire `home/.claude` (source de
  `globalFiles[1]`, `instruction.ts:110-113`), et, pour chaque entrée locale de
  `config.instructions` (`instruction.ts:229-254`), le répertoire parent de la cible. Ces `stat`
  sont des **sentinelles** O(profondeur + cibles config), pas une redécouverte.

Code cible (≤ 15 lignes), principe :

```ts
// instruction.ts — dans systemPaths()
const ctx = yield* InstanceState.context
const config = yield* cfg.get()
const s = yield* InstanceState.get(state)
// config.instructions : répertoire parent de chaque cible locale (les URLs http(s) n'ont pas de répertoire)
const configDirs = (config.instructions ?? [])
  .filter((raw) => !raw.startsWith("http://") && !raw.startsWith("https://"))
  .map((raw) => path.dirname(raw.startsWith("~/") ? path.join(global.home, raw.slice(2)) : raw))
const sentinel = [
  ctx.directory,
  ctx.worktree,
  yield* chainStamp(ctx.directory, ctx.worktree),                 // chaîne scannée par findUp
  yield* dirStamp(global.config),                                 // globalFiles[0] : AGENTS.md global
  yield* dirStamp(path.join(global.home, ".claude")),             // globalFiles[1] : ~/.claude/CLAUDE.md
  ...(yield* Effect.forEach(configDirs, (dir) => dirStamp(dir))), // config.instructions : répertoires hôtes
].join("\0")
if (s.paths?.key === sentinel) return s.paths.value
const value = yield* discoverSystemPaths()
s.paths = { key: sentinel, value }
return value
```

où `dirStamp(dir)` = `mtimeMs` du répertoire (`0` si absent) et `chainStamp(a, b)` concatène
les `dirStamp` de la chaîne `a → b`. Les entrées `global.config` et `global.home/.claude` sont
les deux seules sources de `globalFiles` (`instruction.ts:110-113`), et `configDirs` couvre
`config.instructions` (`instruction.ts:229-254`).

Reste **volontairement inchangé** :

- le cache des **contenus** `reads` (`instruction.ts:158-166`) : on ne touche pas à sa clé
  `size:mtime` ; la mémoïsation des chemins est une couche *au-dessus* ;
- `system()` (`instruction.ts:264`) et `resolve()` (`instruction.ts:310`, `systemPaths()` à
  `:317`) continuent d'appeler `systemPaths()` : le cache est interne à `systemPaths`, donc
  transparent pour les deux appelants ;
- la sémantique « first project-level match wins » (`instruction.ts:209-221`) : identique, on
  met simplement en cache son résultat.

## 5. Alternatives considered

1. **Mémoïser sans invalidation (cache figé pour la session).** Écartée : ne détecte pas un
   `AGENTS.md` ajouté en cours de session, ce qui viole l'exigence du BACKLOG (détection au
   step suivant).
2. **Mémoïser en s'appuyant sur le file-watcher (`file.watcher.updated`).** Écartée :
   l'observateur est **opt-in** (`OPENCODE_EXPERIMENTAL_FILEWATCHER=true`, défaut `false`) ; en
   faire dépendre la correction rendrait la mémoïsation inerte sur une machine sans watcher.
3. **Réduire la fréquence d'appel (appeler `system()` une fois par tour).** Écartée : `system()`
   est appelé depuis plusieurs chemins et doit rester correct à tout instant ; déplacer l'appel
   déplace le problème au lieu de le corriger, sans rien mémoïser.

## 6. Risks

- **Régression tests existants** (fichiers réels à surveiller) :
  `packages/opencode/test/session/instruction.test.ts` — les deux blocs de découverte
  `describe("Instruction.system")` (ligne 203) et
  `describe("Instruction.systemPaths global config")` (ligne 392) —,
  `packages/opencode/test/session/prompt.test.ts`,
  `packages/opencode/src/session/prompt-budget.test.ts` (si l'ordre ou la taille de l'injection
  d'instructions change).
- **Cache périmé — risque principal** : un fichier d'instruction ajouté ou supprimé sans que la
  sentinelle (`mtime` de répertoire) ne bouge serait manqué, et sa modification de contenu
  pourrait être servie depuis un cache. Mitigation : la sentinelle couvre la **chaîne scannée**
  **et toutes les sources de `discoverSystemPaths`** — répertoire de config global, `~/.claude`
  (`globalFiles`, `instruction.ts:110-113`) et répertoires hôtes des entrées locales de
  `config.instructions` (`instruction.ts:229-254`) (ajout/suppression ⇒ `mtime` du répertoire
  hôte change) — et les changements de *contenu* sont déjà couverts par la clé `size:mtime` de
  `reads` ; enfin `config.instructions` est relu à chaque appel (`cfg.get()`,
  `instruction.ts:195`), donc l'ajout d'une entrée est détecté dès l'appel suivant. Le test de
  mutation (§8, cas 3) prouve que c'est bien la sentinelle qui invalide.
- **Coût tokens / latence ajouté** : négatif (gain). Gain ≈ (N−1) × coût d'une découverte par
  tour, le coût résiduel d'une sentinelle `stat` étant O(profondeur). Non mesuré ici, à
  confirmer par la mesure.
- **Sécurité** : aucune. La mémoïsation ne franchit aucun gate de permission et ne lit aucune
  entrée utilisateur ; à surveiller : ne pas partager le cache entre deux `ctx.directory`
  distincts (clé incluant le répertoire, cf. §8 cas 4).

## 7. Acceptance (critère monotone)

Critère **absolu et monotone** (dénominateur = 10 steps, fixe) :

1. **(principal) Total d'appels disque** : sur 10 steps d'une même session, sans changement de
   fichier, le **total** des appels disque attribuables à `systemPaths()` — `fs.findUp`,
   `fs.existsSafe` **et** les `stat` de sentinelle — est **strictement inférieur** au total
   **mesuré sur la même machine avant patch** (§8 cas 1). Aucune composante n'est exclue : le
   patch déplace des appels O(profondeur × cibles) vers des `stat` O(profondeur), et le total
   doit réellement baisser.
2. **(secondaire) Découverte** : le nombre de découvertes complètes (`discoverSystemPaths`
   exécuté) est **≤ 1** sur 10 steps (baseline : 10).
3. **Invalidation** : un fichier d'instruction ajouté en cours de session — soit un `AGENTS.md`
   de projet dans la chaîne `directory → worktree`, soit `~/.claude/CLAUDE.md`, soit une cible
   locale de `config.instructions` (les trois sources sont couvertes par la sentinelle, §4) —
   est **détecté au step suivant** sa création (la liste injectée contient le nouveau chemin).

Commande de mesure : `bun test --timeout 30000 ./test/session/instruction-discovery-cache.test.ts`.
Valeurs attendues :
`total_disk_calls_after < total_disk_calls_baseline` (baseline mesurée avant patch, §8 cas 1) ;
`discovery_calls <= 1` sur 10 steps ;
`newPathInjectedAtStep === stepOfCreation + 1`. Pas de ligne `../BASELINE.md` dédiée à H5 (la
baseline fournie est celle des spawns `git`, H4) ⇒ la baseline disque de H5 doit être **mesurée
localement** avant patch (§8 cas 1).

## 8. Tests

Nouveau fichier : `packages/opencode/test/session/instruction-discovery-cache.test.ts`.
Commande : `bun test --timeout 30000 ./test/session/instruction-discovery-cache.test.ts`.

Cas, avec critère observable :

1. **Comptage disque + découverte** — instrumenter `discoverSystemPaths` (spy) et le
   `FileSystem` (compteur d'appels disque : `exists`/`existsSafe`/`stat`/`findUp`/`glob`) ;
   appeler `instruction.system()` 10 fois sans changer de fichier. Mesurer **avant patch** la
   baseline `total_disk_calls_baseline` ; succès : `total_disk_calls_after <
   total_disk_calls_baseline` (critère principal §7.1) **et** `discovery_calls <= 1` (critère
   secondaire). Le total inclut les `stat` de sentinelle : aucune composante n'est exclue.
2. **Invalidation par ajout** — appeler `system()`, écrire un `AGENTS.md` dans
   `ctx.directory`, rappeler `system()` ; succès : le nouveau chemin est présent (avec un
   `touch`/délai pour garantir la granularité `mtime`).
3. **Test par mutation (garde d'invalidation)** — figer la sentinelle (clé constante) doit
   **manquer** le nouveau fichier : succès = la découverte n'est **pas** relancée et le chemin
   reste absent ⇒ prouve que c'est bien la sentinelle qui invalide (et que le cas 2 teste bien
   quelque chose, pas une redécouverte systématique).
4. **Isolation par répertoire** — deux `ctx.directory` distincts ⇒ clés distinctes (pas de
   fuite de cache d'un projet à l'autre) ; succès : seconde base ⇒ redécouverte (compteur
   incrémenté).

Régression : `instruction.test.ts` (les deux `describe`), `prompt.test.ts`,
`prompt-budget.test.ts`.

## 9. Effort

`S` — un champ de state, une clé de sentinelle et une garde de retour dans `systemPaths()` ;
le coût réel est dans le test d'invalidation (contrôler la granularité `mtime`), pas dans le
patch.

## 10. Verdict self-assessment

`résolu (verdict H5-O1, H5-O2, H5-O3)` — la sentinelle est **(b)** : `chainStamp(directory →
worktree)` **étendue** aux répertoires des deux `globalFiles` (`global.config`,
`global.home/.claude`) et aux répertoires hôtes de `config.instructions` (§4), pour couvrir
**toutes** les sources de `discoverSystemPaths`. Ces `stat` de sentinelle ne sont **plus
exclus** du comptage : le critère principal §7 est le **total** d'appels disque, strictement
inférieur à une baseline mesurée avant patch (§8 cas 1) ; « découverte ≤ 1 » devient
secondaire. Le `mtime` de répertoire reste marqué `INFERE` sur Windows — signal réel mais
**différé** (fenêtre ~1 s) : le cas 2 **avec délai** et le cas 3 (sentinelle figée ⇒ échec
attendu) le confirment (§8), et cette granularité différée est une contrainte du test, pas un
défaut du patch.
