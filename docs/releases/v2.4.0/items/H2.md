# H2 — Cache de prompt explicite sur le provider réellement utilisé

## 1. Problem

Le modèle en service est servi par un provider `openai-compatible`, et pour ce provider la
couche de transformation n'émet **ni point de cache** (`cache_control`) **ni clé de cache de
prompt** (`promptCacheKey`) : chaque appel renvoie donc tout le préfixe au tarif plein, alors que
l'infrastructure de cache existe déjà dans le code mais n'est jamais atteinte sur ce chemin.

## 2. Evidence

`packages/opencode/src/provider/transform.ts:461-476` :

**Conclusion de preuve (PROUVÉ, côté client/émission)** : pour
`opencode-go/deepseek-v4.1-flash`, `ProviderTransform.message` n'entre pas dans `applyCaching`
(aucun `cache_control`) et `ProviderTransform.options` ne pose pas `promptCacheKey`. Aucun point
de cache explicite n'est émis. Le seul cache qui peut subsister est le **cache de préfixe
implicite** du serveur.

`INFERE:` le serveur openai-compatible servi (opencode-go) peut ou non honorer un champ de clé de
cache (`prompt_cache_key`) ou un `cache_control` non standard, et peut ou non implémenter un cache
de préfixe implicite. **Méthode de vérification (à faire, hors périmètre de rédaction)** :
1. intercepter le corps de requête sortant (adapter `CachePrefix` de
   `src/session/llm/cache-prefix.ts`, ou un `fetch` instrumenté) et confirmer les champs envoyés ;
2. rejouer **deux appels identiques** dans une session (rejeu **live** contre l'endpoint réel — un
   serveur scripté fabrique la valeur et ne tranche pas, §8.3) et lire `usage` de la réponse : si un
   champ `prompt_tokens_details.cached_tokens` (ou équivalent `deepseek`) devient `> 0` au 2ᵉ appel,
   le serveur cache ; s'il reste `0`, il ne cache pas ce préfixe ;
3. si le serveur **rejette** un champ inconnu (HTTP 400 « unsupported parameter »), la voie
   « émettre `cache_control` » est fermée et H2 se réduit à la stabilité de préfixe (H3).

BASELINE (reprise, non re-mesurée) : typecheck exit 0 ; suite ciblée
`goal-contract`/`registry`/`parameters` = 86 pass / 8 fail préexistants. Le relevé `cached_tokens`
du provider n'est pas dans la baseline et **doit être établi par la mesure de rejeu live du §8.5**
(contre l'endpoint réel), pas par un serveur scripté (§8.3, plomberie) ni supposé ici.

## 3. Mechanism

Chemin d'exécution de bout en bout, pour une session dont le modèle est
`opencode-go/deepseek-v4.1-flash` :

1. `session/prompt.ts` assemble le tour : `system: string[]`
   (prompt.ts:2258-2341) puis `injected` (volatile) — `prompt.ts:2552-2568`.
2. Le tour part vers `session/llm.ts`, qui appelle la transformation provider ; côté AI SDK, le
   point d'entrée est `ProviderTransform.message` (`transform.ts:461`).
3. La garde `transform.ts:464-476` teste `providerID`, `api.id`, `api.npm` contre l'ensemble
   anthropic/claude/alibaba. Pour `opencode-go` (openai-compatible, `api.id` = `deepseek-v4.1-flash`)
   **aucun terme ne correspond** ⇒ `applyCaching` n'est pas appelé ⇒ **aucun `providerOptions`
   `cache_control` n'est attaché** aux messages système/tools.
4. `ProviderTransform.options` (signature `transform.ts:1065-1069`, corps `:1070-1205`) construit le
   corps de requête. Aucune
   des conditions `promptCacheKey` ne se déclenche pour ce provider :
   `providerID === "openai"` (faux), `providerOptions?.setCacheKey` (faux par défaut),
   la branche `startsWith("opencode")` (faux car gardée par `api.id.includes("gpt-5")`),
   `venice`/`openrouter`/`azure` (faux).
5. Le corps part donc **sans aucun marqueur de cache**. Si le serveur n'implémente pas de cache de
   préfixe implicite, chaque tour refacture l'intégralité du préfixe (system + tools + historique).

Le §4 ajoute, à l'étape 4, une clé de cache **par session** pour la famille compatible, sous une
garde de capacité explicite, sans toucher au mécanisme de breakpoints du §3 (qui reste réservé aux
protocoles qui le comprennent).

## 4. Proposal

**Émettre la clé de cache par session pour la famille openai-compatible servie, et ne PAS émettre
`cache_control` sur un serveur qui peut le rejeter.**

- **Fichier principal : `packages/opencode/src/provider/transform.ts`.**
  - Dans `options()` (autour de `:1119`), remplacer la condition nominative
    `providerID === "openai" || providerOptions?.setCacheKey` par une condition qui couvre aussi la
    famille compatible **lorsqu'une capacité l'autorise**. Deux déclencheurs possibles, à trancher
    en revue (voir §10) : (a) `providerOptions?.setCacheKey` (mécanisme existant, déjà documenté
    `web/.../config.mdx` :371-390), ou (b) un nouveau drapeau de capacité sur le modèle
    (`model.capabilities.cacheKey` ou équivalent) que le catalogue `opencode-go` active pour
    `deepseek-v4.1-flash`.
  - **Ne pas** élargir la garde d'`applyCaching` (`:464-476`) : envoyer `cache_control` à un
    serveur qui ignore ce champ au mieux l'ignore, au pire renvoie 400. L'entrée
    `openaiCompatible` (`:386-388`) reste en place mais **ne doit être activée qu'après** la
    confirmation `INFERE:` du §2.
- **Fichier secondaire : `packages/opencode/src/provider/provider.ts`** — si l'option retenue est
  (b), exposer la capacité au moment de la fusion du modèle (autour de `:1441`, où la famille
  openai-compatible deepseek est déjà reconnue), pour ne pas coder un provider en dur dans
  `transform.ts`.

Code cible (≤ 15 lignes), forme minimale de la clé par session :

```ts
// provider/transform.ts, dans options() — remplace la condition nominative :1119-1121
const wantsCacheKey =
  input.model.providerID === "openai" ||
  input.providerOptions?.setCacheKey === true ||
  // capacité déclarée par le catalogue pour la famille compatible servie
  (input.model.api.npm === "@ai-sdk/openai-compatible" && input.model.capabilities?.cacheKey === true)
if (wantsCacheKey) {
  result["promptCacheKey"] = input.sessionID
}
```

Reste **volontairement inchangé** :

- la boucle de breakpoints `applyCaching` (`:397-418`) et sa garde d'appel (`:464-476`) : les
  breakpoints explicites restent l'affaire des protocoles qui les comprennent ;
- la clé par session (`input.sessionID`) : c'est déjà l'identifiant stable que `promptCacheKey`
  reçoit ailleurs (`:1120`, `:1186`, `:1193`, `:1197`) — on ne change pas la sémantique, on élargit
  l'ensemble des providers qui la reçoivent ;
- `packages/llm/src/cache-policy.ts` : le chemin natif reste borné à
  `anthropic-messages`/`bedrock-converse` (`:42`) ; l'élargir serait un second chantier, hors H2.

## 5. Alternatives considered

1. **Élargir la garde d'`applyCaching` (`:464-476`) à `@ai-sdk/openai-compatible`.** Écartée en
   l'état : émettre `cache_control` (idiome Anthropic) vers un serveur openai-compatible non
   conforme peut produire un HTTP 400 ou être ignoré. Réactivable **seulement** après la preuve
   `INFERE:` que le serveur accepte le champ.
2. **Se reposer entièrement sur le cache de préfixe implicite du serveur (Option 0).** Écartée
   comme correctif : elle ne dépend d'aucun de nos champs et peut déjà être active ; mais elle ne
   répond pas au critère du BACKLOG (« poser la clé de cache là où le provider l'accepte »). Elle
   reste la **hypothèse à réfuter** par la mesure de rejeu live du §8.5 : si `cached_tokens > 0`
   au 2ᵉ appel sans aucun champ, alors H2 devient H3 seul (stabilité de préfixe) — voir §10.
3. **Poser `promptCacheKey` inconditionnellement pour tout provider.** Écartée : un champ inconnu
   dans le corps peut être rejeté par un serveur strict ; et cela romprait
   `test/provider/transform.test.ts` qui pin explicitement les cas `setCacheKey` faux/absent
   (`transform.test.ts:40-83`).

## 6. Risks

- **Régression tests existants** (fichiers réels vérifiés) :
  `packages/opencode/test/provider/transform.test.ts` (encode déjà `setCacheKey` aux lignes
  40-83 — va devoir couvrir le nouveau déclencheur),
  `packages/opencode/test/provider/cache-anchor.test.ts` (modèle anthropic ; ne doit pas changer
  de comportement),
  `packages/opencode/test/session/cache-prefix.test.ts` (observation de préfixe ; le corps
  émis gagne un champ),
  `packages/opencode/test/session/llm.test.ts` et
  `packages/opencode/test/session/llm-native.test.ts` (corps de requête).
- **Coût tokens / latence ajouté** : nul en régime (une clé de chaîne, `~40` octets) ; le gain
  attendu est la baisse du **préfixe facturé au tarif plein**, non démontrée dans cette fiche et
  à mesurer au §8.5.
- **Sécurité** : aucune injection (la clé est `input.sessionID`, déjà utilisée comme
  identifiant ailleurs). À surveiller : ne pas introduire de clé **partagée** entre sessions
  (fuite de préfixe inter-sessions côté serveur) — garder strictement `sessionID`.
- **Réponse provider** : le critère du BACKLOG l'exige — « aucun changement de réponse du
  provider ». L'ajout d'un champ inconnu est précisément le risque ; d'où le test de non-altération
  de la réponse au §8.4.

## 7. Acceptance (critère monotone)

Critère **absolu** (comptes absolus, jamais un ratio dont le dénominateur serait la grandeur que le
patch fait baisser) :

1. **Le champ est bien émis** : sur un provider `opencode-go/deepseek-v4.1-flash` simulé, le corps
   de requête transformé contient `promptCacheKey === sessionID` lorsque le déclencheur est actif,
   et **ne le contient pas** lorsqu'il est désactivé (test par mutation, §8.1-8.2).
2. **Le cache mord — mesure de rejeu live, seule preuve admissible** : la preuve de ce critère est
   un **rejeu instrumenté contre l'endpoint réel** `opencode-go/deepseek-v4.1-flash` (jamais un
   serveur scripté) : deux requêtes identiques dans une même session, `usage` de la réponse réelle
   enregistré. Le nombre de tokens de prompt **facturés au tarif plein** du 2ᵉ appel
   (`prompt_tokens − cached_tokens`) doit être **strictement inférieur** à celui du 1ᵉʳ appel, avec
   `cached_tokens(2ᵉ) > 0`. Référence (BASELINE) : sans le patch, `cached_tokens = 0` aux deux
   appels ⇒ `uncached(2ᵉ) === uncached(1ᵉ)`. **Un serveur scripté (`Bun.serve`, §8.3) ne peut pas
   trancher ce critère** : il fabrique lui-même le `cached_tokens` qu'il est censé observer et ne
   prouve que l'émission de la clé.
3. **Non-altération** : sur le même rejeu live, la chaîne de réponse (`text`) est identique avec et
   sans la clé.

**Si la mesure de rejeu live du critère 2 n'existe pas, le critère 2 est requalifié en
`cached_2 === 0` assumé et documenté, et H2 se réduit à la stabilité de préfixe (H3)** : c'est le
résultat explicitement attendu si `cached_tokens` reste à `0` sur l'endpoint réel avec la clé
posée (le serveur n'honore pas le champ). C'est une décision de repli écrite, jamais une
dissimulation.

Commandes (toutes depuis `packages/opencode` — `bunfig.toml` bloque l'exécution depuis la racine) :
- plomberie (mock) : `bun test --timeout 30000 ./test/provider/prompt-cache-openai-compatible.test.ts` ;
- rejeu live (critère 2) : script hors suite qui appelle l'endpoint réel et journalise `usage` ; la
  valeur brute de `cached_tokens` (1ᵉʳ/2ᵉ appel, avec et sans patch) est archivée à côté de la
  fiche. Comparaison à `../BASELINE.md`.
