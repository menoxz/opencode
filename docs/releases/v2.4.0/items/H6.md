# H6 — Shell persistant (fin du spawn par commande)

## 1. Problem

Chaque appel de l'outil shell démarre un interpréteur neuf ; sur Windows le shell retenu est
`pwsh`, dont le démarrage coûte ~273 ms, si bien qu'une rafale de commandes triviales paie un
coût de démarrage cumulé sans rapport avec le travail demandé.

## 3. Mechanism

Chemin d'exécution de bout en bout qui produit le coût :

1. L'agent appelle l'outil shell ; le code assemble `cmd(input.shell, input.command, input.cwd, input.env)`
   (`tool/shell.ts:627`).
2. `cmd()` (`tool/shell.ts:416`) fabrique un `ChildProcess.make` neuf : sur win32 avec un shell
   PowerShell, il lance `shell -NoLogo -NoProfile -NonInteractive -Command "<utf8 preamble>\n<command>"`.
3. Le spawner démarre le process, `Effect.scoped` enveloppe son cycle de vie
   (`tool/shell.ts:618-633`) ; à la fin de la commande le process est recyclé.
4. La commande suivante repasse par 1–3 : **aucun** process n'est conservé entre deux appels.
   Le coût de démarrage (`pwsh` ≈ 273 ms) est donc repayé intégralement à chaque appel, sans
   rapport avec la durée réelle de la commande (`echo`, `git status`, etc.).

Le §4 corrige l'étape 3–4 : le process est ouvert une fois par session d'agent et réutilisé.

## 4. Proposal

**Décision tranchée sur l'état résiduel (exigence BACKLOG).** La session shell persistante
**isole chaque commande dans un sous-shell** : la commande est enveloppée dans un script block
enfant (`& { … }`) exécuté dans le process persistant, et le répertoire courant est **réinitialisé
explicitement** à `input.cwd` avant chaque envoi. Conséquence **documentée dans le prompt de
l'outil** : variables, variables d'environnement modifiées et `Set-Location` **ne survivent pas**
d'une commande à l'autre ; l'état ne se propage jamais implicitement.

Fichiers modifiés :

- `packages/opencode/src/tool/shell.ts` — introduire un registre de sessions shell indexé par
  `sessionID` (Map), remplacer le `spawner.spawn(cmd(...))` par `registry.run(sessionID, …)` qui
  (a) démarre le process à la première commande et (b) écrit la commande suivante sur `stdin`,
  puis lit jusqu'à un marqueur de fin. Réinitialisation (kill + respawn) si `cwd`, `env` ou
  `shell` diffèrent de la session courante, ou si le process est mort.
- `packages/opencode/src/tool/shell/prompt.ts` — remplacer la phrase `persistent shell session`
  par une description exacte : process persistant **mais état non conservé entre commandes**.
- `packages/opencode/src/session/*` — brancher la fermeture du process sur la fin de session
  (finalizer), pour ne pas laisser de `pwsh` orphelin.

Code cible (≤ 15 lignes), squelette de la seule partie qui change d'invariant :

```ts
// tool/shell.ts — remplace `spawner.spawn(cmd(...))`
const handle = yield* shellSessions.run(input.sessionID, {
  shell: input.shell, cwd: input.cwd, env: input.env,
  command: input.command, // enveloppé côté host : `& { <command> }` + reset du cwd
})
```

Enveloppe envoyée sur `stdin` (host pwsh), principe :

```powershell
Set-Location -LiteralPath <cwd>; & { <command> }; Write-Output "<END-MARKER>"
```

Reste **volontairement inchangé** :

- la politique de permission et de scan (`ask`, `tool/shell.ts:393-414`) : le shell persistant ne
  change pas les patterns de commande autorisés ;
- le parsing tree-sitter des commandes (`tool/shell.ts:438+`) : la validation se fait sur la
  commande brute, avant envoi ;
- la troncature de sortie et la retenue (`list`/`window`, `tool/shell.ts:636-647`) : identiques,
  seule la source du flux change (stdin du process gardé au lieu d'un process neuf).

## 5. Alternatives considered

1. **Isolation par sous-shell *sans* process persistant (spawn par commande, mais moins cher).**
   Écartée : c'est l'état actuel ; le coût est dans le spawn, pas dans le sous-shell. Ne répond
   pas au critère de temps mural.
2. **Réinitialisation explicite sans sous-shell (état partagé, remis à zéro entre commandes).**
   Écartée au profit du sous-shell : la remise à zéro d'une table de variables `pwsh` complète est
   fragile (quelle base ? quelles variables système ?) et non testable de façon déterministe,
   alors que le script block enfant a une frontière de portée définie par le langage.
3. **Passer par un shell bon marché (`cmd`) au lieu de `pwsh`.** Écartée : change la sémantique
   des commandes de l'agent (lot de tests, syntaxe), donc régression fonctionnelle hors périmètre
   performance ; et le gain ne couvre que Windows.

## 6. Risks

- **Régression tests existants** (fichiers réels à surveiller) :
  `packages/opencode/test/tool/shell.test.ts`,
  `packages/opencode/test/tool/shell-launch-retry.test.ts` (le budget de retry au spawn change de
  point d'application), `packages/opencode/test/tool/shell-output-prompt.test.ts`,
  `packages/opencode/test/tool/terminal-output.test.ts`,
  `packages/opencode/test/tool/terminal-output-truncation-root.test.ts`,
  `packages/opencode/test/tool/registry.test.ts`.
- **Fuite d'état non documentée** : c'est le risque principal ; traité par la décision du §4 et
  prouvé par le test de mutation du §8.
- **Process orphelin / verrou** : un `pwsh` gardé qui ne meurt pas au changement de `cwd`/`env`
  ou à la fin de session. Coût : un process résident par session active (~50 Mo RSS `pwsh`),
  borné par le registre et le finalizer.
- **Latence ajoutée** : le protocole `stdin` + marqueur de fin ajoute un aller-retour de framing
  (~quelques ms par commande) — négligeable devant les ~273 ms économisés.
- **Sécurité** : l'écriture sur `stdin` d'une commande déjà validée par le scanner ne contourne
  aucun gate, à condition que **le scan reste sur la commande brute** (§4, inchangé). Risque à
  surveiller : ne pas construire la ligne `stdin` par concaténation naïve (injection via `;`/newline)
  — le framing doit introduire un séparateur non falsifiable, sinon une commande peut simuler le
  marqueur de fin.

## 7. Acceptance (critère monotone)

Critère **absolu** (seuil en ms, pas un ratio dont le dénominateur baisserait avec le patch) :

- Sur win32 avec `pwsh` résolu par défaut, une **rafale de 5 commandes triviales** (`echo`) exécutée
  dans une même session d'agent a un **temps mural médian ≤ 800 ms**.
  Référence : baseline 5 × 272,6 ms ≈ **1 363 ms** (⇒ −41 %, ≥ 40 % requis par le BACKLOG).
- **Aucune fuite d'état non documentée** : une variable posée par la commande *n* est absente en
  commande *n+1* ; un `cd` de la commande *n* ne modifie pas le `cwd` de *n+1* (test du §8).

Commande de mesure (harnais de test, pas une mesure ad hoc) : `bun test --timeout 30000
./test/tool/shell-session.test.ts` — le test lit la durée des 5 commandes et l'asservit à
`< 0.6 × BASELINE_burst`. Valeur attendue : `median_burst_ms <= 800`. Comparaison à
`../BASELINE.md` (démarrage `pwsh` 272,6 ms).

## 8. Tests

Nouveau fichier : `packages/opencode/test/tool/shell-session.test.ts`.

Commande : `bun test --timeout 30000 ./test/tool/shell-session.test.ts`.

Cas, avec critère observable :

1. **Persistance du process** — deux commandes successives dans la même session réutilisent le même
   PID de process hôte (observé via une variable *lue* depuis un fichier temporaire écrit par la
   commande 1 puis relu… non : l'état ne survit pas). Mesure du PID hôte exposé par le registre ;
   succès : `pid2 === pid1` et le second spawn n'a pas eu lieu (compteur de spawns = 1).
2. **Temps mural** — rafale de 5 `echo`, médiane ≤ 800 ms (critère §7).
3. **Test par mutation / anti-régression de l'isolation** — `$x=1` puis lecture de `$x` :
   succès = `$x` absent ; `Set-Location ..` puis `Get-Location` : succès = `cwd` inchangé.
   Ce test **doit échouer** si l'isolation par sous-shell est neutralisée (preuve que le garde
   fonctionne, pas seulement qu'il est présent).
4. **Réinitialisation** — changer `cwd` de la commande suivante ⇒ nouveau process (PID différent),
   ancien process terminé (succès : `pid2 !== pid1` et l'ancien n'est plus vivant).

Régression : relancer `shell.test.ts`, `shell-launch-retry.test.ts`, `shell-output-prompt.test.ts`,
`terminal-output.test.ts`, `terminal-output-truncation-root.test.ts`.

## 9. Effort

réinitialisation, finalizer de fin de session) touche le cœur du lancement de process et doit
rester compatible avec le budget de retry existant.
